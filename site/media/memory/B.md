# B 册｜章节记忆与查用

这份表帮助找回本章重点、短用法和容易混淆的关系，不替代第一次讲解，也不是背完才能继续的清单。

**关系要能解释，常用操作逐渐用熟，长配方带着目的查。** 查用时仍要看懂目标、会改变什么、怎样读结果；不要求先背整段命令再动手。路径、端口、工单编号和输出均为示例，不是当前电脑的运行状态。

**表里的英文名称先看它的中文作用和交接位置，不是要求全部背下来。** 代码名、HTTP 字段和命令是回到正文或实验中查找的锚点；先能说清谁把什么交给谁，再逐渐认熟常用写法。

B 册连接的是：**程序里的值 → 请求消息 → 接收方的函数 → 回应消息 → 后续可使用的值。** B01 看消息，B02 看接收方，B03 看调用方；B04 连接两段交换的证据，B05 用创建和读回完成一次使用。章节号帮助定位，这些位置属于同一条关系。

下文“回看”指 B 册原教材的同名小节，另有明确注明的 A10 入口。按当前问题找即可，不要求先读完全部表格。

## B01｜两个程序怎样交换一条工单？

A 册里的函数交接本程序中的值；B01 把交接扩展到另一个运行中的程序：**交去标题与优先级 → 服务创建记录 → 回应交回编号 → 下次用编号读取。** 两端不共享一个 Python 变量。

### 先认清：谁交给谁，交的是什么？

| 当前问题 | 关系或短用法 | 记到什么程度 |
|---|---|---|
| 哪一边是客户端，哪一边是服务端？ | 本次发请求的是 client，接收、处理并回应的是 server；同一电脑的两个进程也能承担这两个角色。 | 认熟 request／response 的方向；角色跟着这次交接判断，不是固定的设备种类。 |
| HTTP、API、JSON 是同一个东西吗？ | API 约定怎样使用能力；HTTP 规定请求与回应怎样表达；JSON 表示其中的结构化数据。 | **能把三者放回同一次交接。** HTTP 不只传 JSON，API 也不全使用 HTTP。 |
| 一条消息怎样读？ | 请求先看 method 和目标，再看 headers、body；回应先看 status，再看自己的 headers、body。`Content-Type` 声明这份 body 的类型。 | 逐渐认熟位置，不手拼或背完整报文。请求头和响应头分别属于各自的消息。 |
| `201` 和 `"status":"open"` 都是状态，有什么不同？ | `201 Created` 说明这次创建请求的结果；`open` 是工单的业务状态；都不是程序退出码。 | **请求结果、资源状态、进程退出分开。** 一次 404 不表示服务进程退出。 |
| 为什么不把字典直接交给另一边？ | `dict` 是本进程的对象；传送的是 JSON 表示的字节，另一边解析后得到自己的值。 | 字段相同不等于共用对象；修改客户端字典，不会自动修改服务端记录。 |

第一次先沿标题、优先级和返回编号看清消息交接，不需要先手写序列化。要查字典怎样变成传送内容时，再认两个方向：`json.dumps(值)` 产生 JSON 文本，`json.loads(文本)` 解析出 Python 值；UTF-8 的 `encode`／`decode` 连接文字与字节。这些转换本身不发送请求，实际调用可由 HTTPX 的 `json=` 等工具承担编码。

JSON 的 `true`、`false`、`null` 对应 Python 的 `True`、`False`、`None`，字符串与对象键使用双引号。**合法 JSON 也可能是列表、数字，不一定是当前需要的字典。** 引号和转义交给库处理，不靠拼字符串凑格式。

回看：「HTTP、API 和 JSON 各自负责什么？」「Python 字典看起来像 JSON，为什么还要转换？」。

### 地址选哪里，动作想做什么？

| 当前问题 | 关系或短用法 | 记到什么程度 |
|---|---|---|
| 完整 URL 里分别在找什么？ | `http://127.0.0.1:8000/tickets/T-42?include_history=true`：协议、主机、端口确定服务入口；path 选工单，query 调整本次读取。 | 能分清目标与选项；编号和端口用实际值，不背样例。 |
| URL path 是磁盘路径吗？ | `/tickets/T-42` 由服务解释，不要求磁盘有同名目录。`127.0.0.1` 指当前电脑自身，换电脑就换了“自己”。 | **URL 路径不等于文件路径，回环地址不指向另一台电脑。** `https` 使用加密保护的 HTTP 连接。 |
| 创建和读取分别怎么表达？ | 本例 `POST /tickets` 提交 JSON 创建；`GET /tickets/T-42` 读取。`?include_history=true` 要求附带历史，不更换编号。 | 逐渐用熟 GET 读取、POST 在本例中创建；URL 中的 `true` 是文字，服务处理后才成为 Python 值。 |
| 再发一次，效果也只是一次吗？ | 本例重复 POST 会新建另一条记录。GET 的读取语义不要求改变资源；幂等指重复同一意图的预期效果与一次相同。 | **别因标题相同就放心重发创建。** 幂等不要求每次响应内容或状态码都相同。 |

其他方法按意图查：PUT 通常完整替换，PATCH 局部修改，DELETE 删除；当前配套还实现了 PATCH 状态修改。GET、PUT、DELETE 有幂等语义，POST、PATCH 没有普遍保证。safe 指请求语义不要求改变资源状态，不是保密。方法名不能替代当前 API 的具体约定，也不能让尚未实现的入口自动存在。

回看：「完整地址怎样选中刚才那条工单？」「为什么创建用 POST，读取用 GET？」。

### 页面显示成功以后，还要看什么证据？

| 当前问题 | 关系或短用法 | 记到什么程度 |
|---|---|---|
| `200` 就能直接用 body 吗？ | 成功状态之后，还要检查内容类型、能否解析及所需字段。声明是 JSON，正文也可能损坏或缺字段。 | **成功状态不替内容作保证。** B03 再展开每一步。 |
| 不熟悉状态码时先看哪里？ | 2xx 成功；3xx 涉及重定向等处理；4xx 与请求、身份或目标等问题有关；5xx 表示服务未正常完成处理。 | 认熟大类和正在用的具体码，其余查。404 可能是路径拼错，也可能是工单不存在，数字不能单独定位。 |
| `Accept` 和 `Content-Type` 差在哪？ | 前者表达希望收到的类型，后者声明当前消息实际发送的类型；希望不等于对方一定满足。 | 认清两个方向；`Authorization`、Cookie 的完整用法按需查，分享记录前去掉凭据和敏感内容。 |
| 怎样核对真正发生的交换？ | 在 Network 选中本次 POST `/tickets`，对照 URL、method、status、Payload 和 Response；下一次 GET 使用这次返回的 `id`。 | 逐渐能找对记录并读懂结果；不要把 `/docs` 页面或 `/openapi.json` 的加载当成创建。 |

地址栏适合发起读取，粘贴 URL 不会自动带 JSON 发 POST。`/docs` 帮助手工构造请求，Network 观察浏览器实际交换，HTTPX 用于 Python 主动调用；它们各解决不同问题。启动服务的完整准备查 B05，不先背配方。

回看：「状态码成功，正文就一定能用了么？」「Header 里除了内容类型，还可能有什么？」「页面写着“创建成功”，怎样看到实际交换？」。

本章看清消息交接；B02 打开接收方，看 **method/path 怎样找到函数，JSON 怎样成为参数，返回值怎样成为响应**。

## B02｜请求怎样进入 Python 函数？

本章看服务端接手的顺序：**收到请求 → 匹配入口 → 解析并检查输入 → 函数处理当前状态 → 检查公开结果 → 形成响应。** 重点不是默写整份服务，而是知道失败时已经走到哪里。

### 请求和函数之间，谁在牵线？

| 当前问题 | 关系或短用法 | 记到什么程度 |
|---|---|---|
| 有了 `app = FastAPI()`，服务就监听了吗？ | 它建立应用对象；Uvicorn 加载应用并监听，FastAPI 负责接口处理，业务函数决定工单怎样变化。 | **应用定义、实际运行、业务处理分开。** 导入框架不等于端口已经可用。 |
| 请求没写函数名，怎么找到代码？ | `@app.post("/tickets", status_code=201)` 登记 POST、路径和紧随其后的函数。加载时登记，匹配请求后才调用。 | 认熟 method＋path 选择入口；函数叫 `create_ticket` 不会自动形成 HTTP 入口。 |
| JSON 怎样成为函数可用的值？ | `payload: CreateTicket` 让框架按模型解析、检查 body，再把对象交给参数；`payload.title` 取属性。 | 知道检查由框架执行；普通 Python 类型注解本身不会自动校验所有函数调用。 |
| path、query、body 中的值从哪取？ | 本例路径中的 `{ticket_id}` 接编号；`include_history: bool = False` 接 query，转换并提供默认值；创建内容进 body model。 | 能指出“处理谁、读取选项、提交内容”的位置。`response: Response` 由框架提供，不是客户端填入的字段。 |
| `print` 和 `return` 都能回应吗？ | `return record` 把值交给框架组织响应；`print(record)` 写到服务输出。 | **返回给代码与显示到终端分开。** 服务打印了记录，不表示客户端已收到它。 |

`mini_api:app` 读成“`mini_api` 模块中的 `app` 对象”，不是带冒号的文件名；完整启动参数查用。这个小例也不替换完整配套 `app.py`。

schema 描述允许的数据形状，不是某次具体值。`Field(ge=1, le=3)` 表示至少 1、至多 3，`Literal[...]` 限定取值；需要改字段时查模型。FastAPI 据 route、模型等声明生成 `/openapi.json` 和 `/docs`，**文档反映声明，不替代实际请求验证**。

回看：「先让一条请求找到一段代码」「FastAPI 和启动服务的工具是什么关系？」「接口文档怎么知道要填写哪些字段？」「URL 里的编号和选项怎样进入函数？」。

### 这次拒绝发生在哪里，之前有没有改过状态？

| 当前问题 | 关系或短用法 | 记到什么程度 |
|---|---|---|
| 合法 JSON 就能进入创建函数吗？ | `"priority":"urgent"` 可解析，却不满足输入模型；本例 422 在创建函数前发生，没有新增记录或消耗编号。 | 区分 JSON 解析和输入校验。默认配置也可能把数字文字转换为整数，不概括成“所有字符串都拒绝”。 |
| 得到 404，函数一定没运行吗？ | 路径未匹配可以 404；匹配后查不到工单，也可以由函数返回 404。`raise HTTPException(...)` 把失败交给框架形成回应。 | 看目标和错误证据；只在返回字典里写“错误”不会自动改变状态码，抛 HTTPException 也不等于杀掉服务。 |
| 版本号类型正确，为什么还是拒绝修改？ | 模型查形式和范围；函数比较 `expected_version` 与当前记录，不同返回 409，相同才修改并增加版本。 | **输入合法不等于当前业务条件成立。** 示例内存中的先比较再写，没有并发原子保证。 |
| 内部结果为什么不全发出去？ | `response_model=TicketPublic` 检查公开形状、过滤未声明字段，内部存储的字段没有因此删除。 | 区分内部记录和公开表示；输出过滤不替代权限判断。 |
| 服务自己返回错字段，为什么不是 422？ | 服务违背自己的输出约定，正常运行默认形成 500；此前已发生的写入不会自动撤销。 | **错误归属与业务效果分别判断。** 收到失败，不等于创建从未发生。 |

读取历史时怎样复制字典和列表、选择是否返回历史、是否省略 `None`，都在原章查用。这里要保留的关系是：改变公开表示不应意外改坏内部记录；浅拷贝也不等于复制全部嵌套对象。

回看：「为什么先检查输入，再运行创建函数？」「得到 404，说明函数没有运行吗？」「输入都合法了，为什么还可能不能修改？」「函数 return 的内容，为什么不全部交给客户端？」「服务自己返回错了字段，为什么不是 422？」。

### 测试、状态与配置，分别看哪一段？

| 当前问题 | 关系或短用法 | 记到什么程度 |
|---|---|---|
| 直接调函数，与测试一次接口差在哪？ | TestClient 在测试进程内把请求交给应用，经过路由、解析和校验，不需要真实监听端口。 | 逐渐用熟 `client.post(..., json=...)`、`status_code`、`json()`；**接口测试通过，不证明端口在监听。** |

回看：「怎样检查整个接口，而不只检查函数？」「哪些值属于请求，哪些值属于运行配置？」。

服务端检查了自己的处理，但客户端面对的是**实际收到的回应**，不能假定它必然符合意图。B03 从这个边界继续。

## B03｜怎样只把可用回应交给后续代码

本章换到调用方：**Python 值 → HTTPX 请求 → 检查回应 → 只交回可用摘要。** FastAPI 接收处理，HTTPX 主动发送；不是让两个程序直接调用彼此的 Python 函数名。

### 请求发给谁，值放在哪里？

| 当前问题 | 关系或短用法 | 记到什么程度 |
|---|---|---|
| 怎样把一次调用变成请求？ | `client.post("/summaries", ...)` 选 POST 和 path，`base_url` 提供服务地址；`json={"text": text}` 编成 JSON body，并设置相应内容类型。 | 逐渐用熟“地址、方法、内容”的组合，端口和样例文字不背。 |
| `params=`、`json=`、`headers=` 能互换吗？ | 分别放 URL query、JSON body、消息头；放哪里由当前 API 约定决定。 | **直接分清三个位置。** 具体字段查接口，不能只因都在传值就互换。 |
| 收到的 `.text` 和 `.json()` 差在哪？ | `response.text` 是解码后的正文文字；`response.json()` 尝试解析成 Python 值。 | 认熟“文字 → 值”的方向；解析不会顺带证明成功或字段正确。 |

`Accept` 表达希望收到的类型，仍要核对实际回应。本章 `X-Request-ID` 在 header 中关联记录，不是正文，也不是工单编号；B04 再把它串到两端。

回看：「先把一次普通调用读完整」「`Response` 到手，还没有到可以使用摘要的时候」。

### 回应到手后，怎样变成可以使用的结果？

本章的先后关系是：**成功状态 → 约定的内容类型 → JSON 能解析 → 类型和字段可用 → 返回摘要。** 过了前一关，只允许走到下一关。

| 当前问题 | 关系或短用法 | 记到什么程度 |
|---|---|---|
| 有 `Response`，是否已经成功？ | 失败也会有回应。`response.raise_for_status()` 对非 `2xx` 抛出 `HTTPStatusError`；失败正文也可能是合法 JSON。 | **拿到回应不等于拿到可用结果。** 若合同要求精确 200 或 201，还需单独比较。 |
| 内容类型怎样判定？ | 本例要求 `application/json`，先处理大小写、空白和分号后的参数，再精确比较；缺失或其他类型都拒绝。 | 理解“规范化后精确比较”，整行字符串配方查用，不记成“包含 json 就行”。 |
| 声明 JSON 就能解析吗？ | 声明正确，body 仍可能损坏；`response.json()` 只处理解析。反过来，`text/plain` 的正文恰好能解析，也未满足本例合同。 | **声明、JSON 语法、接口合同分开检查。** |
| 能解析，为什么还不能直接 `.strip()`？ | 先确认顶层是 `dict`，再取 `summary`；确认摘要是 `str`，才能去两端空白，再拒绝空结果。 | 顺序取决于下一步操作的前提；列表、缺键、数字、只有空格都不满足本例的摘要约定。 |
| 哪一步才交给后面？ | 所有检查通过才 `return summary`；在 `summary = request_summary(...)` 中，右侧成功返回，左侧本次赋值才完成。 | 能沿返回追踪；失败时残留的旧摘要不能冒充本次结果。 |

查用时，规范化就是取第一个分号前的部分，去两端空白、转小写。例如 `Application/JSON; Charset=UTF-8` 得到 `application/json`。这是本接口的合同，其他接口可约定不同类型。HTTPX 默认不跟随重定向，本章 302 也在状态检查处停止；`raise_for_status()` 本身不负责跳转。

回看：「先检查 status，因为失败回应也可能带着 JSON」「内容类型、JSON 语法和字段，是三件不同的事」「把这些检查接成一个有明确出口的函数」。

### 同样叫失败，最早停在哪里？

| 当前问题 | 关系或短用法 | 记到什么程度 |
|---|---|---|
| 没取得完整回应，就先去读 status 吗？ | transport 路线在 `client.post(...)` 抛出 `RequestError` 或子类，本次 `response = ...` 没完成，状态检查尚未开始。 | 先认失败层，不读尚未取得的回应；**客户端没拿到，不证明对方没执行。** |
| 收到 503 后停止，与连接失败有什么不同？ | status 路线已有回应，`raise_for_status()` 抛 `HTTPStatusError`，可从 `exc.response` 查看那份回应。 | 分清“没取得完整回应”和“回应报告非成功”，不全叫网络断了。 |
| 200 后仍失败，查哪里？ | content 路线可能停在媒体类型、解析、顶层类型、字段或非空检查；小例用 `ValueError` 表达坏内容。 | 找最早未通过的一关，不把所有问题归给 `.json()`。 |
| 单独处理超时，`except` 顺序为什么重要？ | `TimeoutException` 属于 `RequestError`，先接具体超时，再接宽泛请求错误，否则超时会被先接走。 | 能解释分类为何丢失；完整异常名和分支查正文，不成套背诵。 |

本章用 `try/except/else` 分开失败处理和成功显示。接住异常不等于补出了成功值；无关计算不要混入同一个 `try`，免得其 `ValueError` 也被误报为供应商坏内容。

回看：「同样一句“调用失败”，最早停止的位置可能不同」。

### 等待、复用与受控测试，各自改变哪一段？

| 当前问题 | 关系或短用法 | 记到什么程度 |
|---|---|---|
| `timeout=1.0` 是整次调用的一秒总限时吗？ | connect 等建连接；read 等收到下一块响应数据；write 等写出下一块请求数据；pool 等可用连接。它们不是同一只总秒表。 | **认清等待位置，不能承诺整次一秒内结束。** 数值和异常子类全名可查。 |
| 反复调用，为什么保留一个 Client？ | `httpx.post(...)` 适合一次临时调用；保留 `Client` 可复用连接、集中配置。每次 request/response 仍是独立消息。 | 按使用方式选入口；每轮重建 Client 不等于跨轮复用。 |
| Client 用完，谁收尾？ | `with httpx.Client(...) as client:` 离开区间时关闭资源，包括异常退出；长运行应用也可持有它并安排停止时关闭。 | 认熟“建立者安排收尾”，关闭客户端不等于停止远端服务。 |
| 不启动服务，`MockTransport` 测到什么？ | 它接到 HTTPX 构造好的 request，返回受控 Response 或抛异常；可核对请求内容和客户端处理分支。 | 理解替换点；主动抛 `ReadTimeout` 不证明真实等过一秒，也不证明网络接通。 |
| `SupplierClient` 为什么让调用变短？ | 它集中发送和回应检查，成功交回摘要，失败翻译为本应用异常；检查没有消失，只移到适配层。 | 多处需要统一合同才更有价值；一次临时调用可直接用 HTTPX，不为形式加包装。 |

查配置时，`httpx.Timeout(1.0, connect=2.0)` 表示连接等待两秒，其余等待一秒。超时结束等待，不取消对方已做的工作，也不自动重试。`trust_env=False` 是本地练习隔离代理环境影响的选择，不是所有项目必选项；真实凭据来自配置，不放 URL 或日志。

适配层自定义的失败名称在 B04 与外层回应一起查，不另背一套词表。`raise ... from exc` 保留底层原因，不抵消失败。应用创建的客户端由应用收尾；测试传入的替身由提供方管理。

回看：「多次调用同一个服务，为什么保留一个 Client」「一秒 timeout 到底限制哪段等待」「不启动网络服务，也能检查客户端如何面对回应」「已有的 SupplierClient 包装，究竟增加了什么」。

B04 把调用方放进另一个服务内部：**本地 API 接收用户请求，又去请求供应商。** 两次交换各有回应，不能混成一次。

## B04｜两次 HTTP 交换怎样找到失败位置

本章把位置串起来：**调用者 → 本地 API → 供应商 → 本地 API → 调用者。** 这是两次 HTTP 交换；本地代码中间还通过 `return` 交值，不是一份回应从头穿到底。

### 谁接收请求，谁检查结果？

| 当前问题 | 关系或短用法 | 记到什么程度 |
|---|---|---|
| 本地 API 到底是 client 还是 server？ | 对最初调用者是 server，请求供应商时是 client。 | **角色跟着交换判断。** 两份回应有不同接收者和内容约定。 |
| 发给供应商的内容从哪里来？ | `ticket_id` 来自 path，`payload.text` 来自 body，关联标识来自 header；先确认工单存在，再发送本次 body 文字。 | 本例不自动读取工单全部内容；目标编号、待处理文字、关联标识各有用途。 |
| header 怎样继续传给下游？ | 本例 `Header(default=None)` 接收可缺少的请求头，`x_request_id` 对应 `X-Request-ID`；取得值后放到 HTTPX 的 `headers`。 | 认熟“header → 参数 → 下游 header”；完整声明和编号生成查用。 |
| 供应商成功，结果怎样到最初调用者？ | adapter 返回受检摘要字符串；endpoint 加入 `ticket_id`、`request_id`，交给输出 model，再形成外层回应。 | **内部 return 交值，HTTP response 跨进程交消息。** 内层 200 不单独证明外层成功。 |
| 本地输入不合格，供应商会收到吗？ | 文字长度不合格时 422，endpoint 未开始；工单不存在时 404，supplier 调用尚未发生。 | 从最早停止的位置判断后续是否发生，不把所有失败归给供应商。 |

关联标识怎样回到成功、失败、输入校验回应，处理关系查原章：普通 `response.headers[...]` 不会自动替另一份 `HTTPException` 回应补 header；422 又可能发生在 endpoint 之前。需要改 422 处理器时，完整实现查配套 `app.py` 的 `validation_error_handler`，流程说明不等于完整代码。

回看：「本地 API 既接收请求，也会发出请求」「Header 怎样进入函数，再进入下一次请求」「本地 API 先决定输入能否继续」「成功时，有两份回应和一次本地返回」「空文字为什么只能得到一段 HTTP 交换」。

### 看见失败状态，先说清它属于哪一段

| 当前问题 | 本章应用的失败路线 | 记到什么程度 |
|---|---|---|
| 供应商 500，为什么调用者看见 502？ | 内层 500 → `SupplierBadStatus` → 本地 endpoint 选择外层 502，`detail` 是 `supplier_bad_status`。 | **两份回应、两个状态。** 不是 HTTPX 自动改码，也不是所有应用必须这样映射。 |
| 外层有 504，为什么又说没有完整回应？ | 内层读取超时，未取得完整 Response；本地接住 `SupplierTimeout`，另给外层 504。 | 带上观察位置；**超时不证明供应商没执行，也不撤销其工作。** |
| 连不上，与读取超时相同吗？ | 其他请求失败走 `SupplierUnavailable`，本地回答 503；超时走 504。 | 保留原因，不只记“网络错了”；尝试调用不证明对方已收到。 |
| 供应商 200，外层也可能 502 吗？ | 媒体类型、JSON 或摘要字段不合约 → `SupplierBadContent` → 本地 502，`detail` 是 `supplier_bad_content`。 | 同为 502，断点可能不同；结合 detail 与日志判断。 |

本例用假供应商延迟回应形成 read timeout；具体等待秒数是受控配置，不用背，也不代表整条业务路线的总限时。

回看：「供应商已经返回500，本地为什么选择回答502」「超时路线缺的是供应商完整回应，本地仍然可以回答504」「连接失败和坏内容也要保留自己的原因」。

### 怎样把证据对应回这一次处理？

| 当前问题 | 关系或短用法 | 记到什么程度 |
|---|---|---|
| `request_id` 与工单 id 一样吗？ | 工单 id 指业务记录；request_id 关联一次处理。同次跨服务工作沿用，新的一次外部请求使用新标识。 | **关联不证明成功，不授予权限，也不自动防重复。** 示例编号不背。 |
| `supplier_call_started` 就证明对方收到吗？ | 它表示本地进入调用位置；供应商的 `supplier_request_received` 再补接收证据。`supplier_call_succeeded` 表示 adapter 拿到受检摘要，仍在外层输出前。 | 按事件位置读：开始、内层成功、外层完成不是同一件事。 |
| 浏览器 Network 能看全程吗？ | 它看到浏览器的外层交换，看不到本地 Python 自己发出的内层请求；用 request_id 再追服务日志。 | 先找观察者的位置；仅有 ID 没有事件与结果，还不能还原经过。 |
| 核对零调用、参数与公开错误，用什么？ | 记录型 supplier 替身接在 endpoint 后，保存调用或抛指定异常；已有历史记录时看本次是否新增。 | 它检查函数交接；B03 的 MockTransport 检查 adapter 的 HTTP 处理，两者替换位置不同。 |
| 替身通过，能证明两个服务接通吗？ | 不能；两服务实际启动并交换消息才增加跨进程证据。假供应商按固定规则回答，不是真实模型。 | **各证据只证明自己的范围。** 本机 fake 通过不扩大为生产或客户环境已验证。 |

日志保留阶段、标识和必要状态，不靠保存 token 或整段敏感正文换取关联能力。INFO 事件还需实际日志配置；屏幕没显示，不能单独证明没调用。例如外层 502 与同 ID 的 `supplier_status=500` 合起来，才能找到“内层已有回应，在状态检查处停止”。

回看：「两条请求交错时，怎样知道一行日志属于哪次工作」「日志记录阶段，使处理经过可以被读回」「最初调用者的 Network 能看到哪一段」「先在函数交接处固定结果，再经过两个真实服务」「真实双服务验证要把不同请求分别认出来」。

本章留下的是 **哪段交换、最后成立的事实、最早失败的位置**；B05 把这些用于一次完整使用。

## B05｜创建之后，怎样读回同一条记录？

本章整合 **创建输入 → 服务建立记录 → 回应交出 id → 用这个 id 查询 → 比较读回结果**。重点是把上一次的结果交给下一次，不是再记一套框架名。

### 怎样确认两次请求操作的是同一条记录？

| 当前问题 | 关系或短用法 | 记到什么程度 |
|---|---|---|
| 查询编号从哪里来？ | `ticket_id = created["id"]` 取本次创建编号，再交给 `get_ticket(client, ticket_id)` 发查询。 | **上一次实际结果决定下一次目标。** 不把 `T-42` 写死为每次的答案。 |
| 读回成功，只看 200 够吗？ | 本例没有中途修改时，`assert fetched == created` 比较五个公开字段；类型正确还不证明是本次记录。 | 认熟比较关系，完整检查脚本查用；取字典值本身不发送请求。 |
| 创建 201、查询 200、退出 0 各证明什么？ | 服务日志记录 HTTP 状态；脚本比较公开结果。退出 0 不等于严格断言了每个具体状态。 | **证据检查到哪，结论才到哪。** 响应成功、结果相同、程序正常结束分别看。 |
| 服务检查过了，客户端为什么还查？ | 服务检查自己的处理；客户端检查实际收到的状态、JSON 类型、解析结果和字段，保护后续使用。 | 不把 `.json()` 当成完整检查；`id/title/status` 要字符串，`priority/version` 要整数且排除 bool。 |

本例用 `type(value) is int` 排除 `True`：Python 中 bool 与 int 有继承关系，但字段合同不接受布尔优先级。该写法按需查；关键是 **结构类型与业务对应关系是不同的检查**。关闭 HTTPX Client 只收尾客户端资源，不会停止另一个窗口的服务。

回看：「两次交换怎样连成一件事？」「用本次返回的编号，再发一次查询」「为什么服务检查过了，客户端还要检查？」。

### 要运行时，怎样找到同一份项目和自己的服务？

| 当前问题 | 关系或短用法 | 记到什么程度 |
|---|---|---|
| 在哪里建立环境、加脚本？ | 从可见入口 `01_配套代码_A-E → examples → b_http_api → ticket-api` 进入，把整个项目复制到自己的新实验目录；有副本则继续原副本，不覆盖或合并已有修改。它与命令里的底层路径 `01_配套练习` 指向同一份文件。 | 用自己的副本，不在随书参考目录安装或产生运行状态；路径是定位入口，不是必背内容。 |
| 两个窗口怎样确认没走错？ | 各自用 `Get-Location` 看位置、`Get-ChildItem` 看文件，都进入同一副本；应有 `app.py`、`client.py`、`requirements.txt`。 | 逐渐认熟查看位置与文件；新窗口不会自动跟随另一窗口后来改变的位置。 |

| `app:app` 怎样读，要开几个窗口？ | 前者是模块，后者是应用对象。普通创建查询用服务＋客户端两窗口；双服务摘要用两服务＋客户端三窗口。 | 窗口用于观察不同进程，不是业务按窗口先后自动执行；完整启动命令不用背。 |

本例用 `127.0.0.1` 绑定本机，8000／8001 匹配两个服务配置，不要求背数字。双服务准备在专用新窗口指定本机供应商，并移除该窗口继承的供应商 token；只影响该窗口环境，不删除秘密文件或改系统设置。需要运行时完整看原章准备，不从半行提示猜操作。

### 失败后留下什么，下一步靠什么判断？

| 当前问题 | 关系或观察入口 | 记到什么程度 |
|---|---|---|
| 创建输入被拒绝，后面的查询会发生吗？ | 本例 `"urgent"` 优先级在输入校验处 422，创建正文未运行；客户端状态检查停止，没有这次成功的 `created`。 | 沿最早断点判断：取编号、查询、比较还没有机会执行。 |
| 创建成功，后来查询失败，会撤销创建吗？ | 查不存在的编号返回 404；前一次创建仍已发生。 | **多个请求连起来，不自动成为同进同退的一次操作。** |
| 创建请求超时，可以当作没创建再发吗？ | 没取得完整回应，服务也可能已经执行；先找服务端证据，不盲目重复创建。 | 与函数前的输入拒绝分开判断，timeout 不证明业务效果为零。 |
| 故意检查 502、504，为何不用成功状态检查？ | 这次要接收并比较预期失败；`raise_for_status()` 常用于阻止正常业务继续用坏结果。 | **按目的选动作**，测试失败路线不必照抄正常成功路线。 |
| 测试、真实调用、日志怎样配合？ | 测试检查既定条件与分支，本机真实调用补进程和连接证据，日志帮助追已记录的阶段；替换位置的具体区别见 B04。 | 它们不互相替代，没看到日志也不能单独证明零调用。 |
| 重启后记录去哪了？ | `app.state.tickets` 的内存随服务停止消失，新应用建立空状态。 | **HTTP 交接正确不等于持久保存。** C 册用独立练习连接数据库，不假定共享此项目的库或状态。 |

双服务验证时，每次外部请求用自己的 request_id，在那次跨服务处理中沿用。外层 502 可能对应内层 500；外层 504 不表示供应商返回过 504。输出几个状态数字只是结果，还需把它们对应回实际发生的事件。

回看：「改一个地方，看看失败从哪里开始」「两个服务的调用，要观察哪两段？」「测试、真实调用和日志，各多看到了什么？」「服务重启后，为什么记录不见了？」。
