# C 册｜章节记忆与查用

这份表帮助找回本章重点、短用法和容易混淆的关系，不替代第一次讲解，也不是背完才能继续的清单。

**关系要能解释，常用操作逐渐用熟，长配方带着目的查。** 查用时仍要看懂目标、会改变什么、怎样读结果；不用先背下完整建表、连接配置或迁移程序。

**表里的 SQL、函数和配置名先看它们在数据流中的作用，不是背诵清单。** 中文说明负责建立关系；名称保留作查找入口，真正需要写时再回到当前表结构和示例核对。

C 册让应用接上长期事实：**查询决定这次怎样回答，结构和约束决定哪些事实可以保存，事务决定哪些改变一起完成，日志与实测说明一次操作发生了什么。** SQL 是表达这些要求的语言；SQLite 是执行它们的数据库引擎；Python 的 `sqlite3`、SQLAlchemy 是程序访问数据库的入口。

下文“回看”指 C 册原教材的同名小节，跨章处另有注明。各章小库不是一份不断追加的数据库：C03、C04 共用业务结构；C01、C02、C05、C06 使用各自说明的独立实验。相同表名不保证列相同，整段运行准备应查当前章。编号、日期与结果都是合成示例，不是当前电脑的数据或运行状态。

## C01｜查询为什么得到这些行，而不是另外几行？

本章先分开**原表保存了什么**与**这次答案需要什么**。一条查询能够运行，还要能解释为什么恰好留下这些行、这些列和这个顺序。

### “最早三条”包含哪几个决定？

| 当前问题 | 关系或短用法 | 记到什么程度 |
|---|---|---|
| 一行、一列、`id` 分别表示什么？ | 本章一行是一条预约，一列是在各行含义一致的字段；`id` 区分预约。 | 先认清当前表的一行含义，不能只凭表名猜列。查询后的一行含义还可能改变。 |
| 一条 SELECT 怎样读？ | `FROM` 选输入；`WHERE` 选行；`SELECT` 选结果列；`ORDER BY` 定顺序；`LIMIT` 限数量。 | 逐渐用熟这些位置；**筛选、排序、限量分开。** 这是解释答案的关系，不是断言引擎内部必定按此搬动数据。 |
| `LIMIT 3` 为什么不等于“最早三条”？ | 没有 `ORDER BY` 就没有要求最早。`ORDER BY starts_at ASC, id ASC` 先按时间升序，再用唯一编号打破并列。 | “最早／最近”要想到顺序；`ASC` 升序、`DESC` 降序随问题选择，不能依赖某次碰巧的显示次序。 |
| 没出现在结果中，就是删除了吗？ | `WHERE` 可排除行，`LIMIT` 可截掉符合条件但排在后面的行；`SELECT` 都没有因此修改原记录。 | **读取答案与改变事实分开。** 显示三条，不证明原表或符合条件的记录只有三条。 |

原章查询的短用法是：

```sql
SELECT id, starts_at, customer_name
FROM appointments
WHERE starts_at >= '2026-08-22 00:00'
  AND status != 'completed'
ORDER BY starts_at ASC, id ASC
LIMIT 3;
```

在本章六条记录中：筛选留下 `101、102、103、106`，排序后为 `101、106、102、103`，最终取 `101、106、102`。103 符合条件，只是排在第四。`completed` 是业务采用的状态文字，SQL 并不知道“完成”的含义；这里的状态都有值。

SQL 文字值使用单引号，`AS` 可给结果列起名字，分号标记语句结束。这些写法逐渐认熟，不用背例子的日期、姓名与编号。

回看：「先看清楚，表里到底有什么」「“最早三个未完成预约”要做哪几个决定？」「去掉排序，为什么不再能证明“最早”？」。

### 未知值、时间边界和文字条件怎样选？

| 当前问题 | 关系或短用法 | 记到什么程度 |
|---|---|---|
| 没填备注，为什么 `note = NULL` 查不到？ | `NULL` 表示未知；普通比较得到未知，`WHERE` 只留真。用 `note IS NULL` 或 `note IS NOT NULL`。 | **直接分清 NULL、零、空文字和字符串 `'NULL'`。** 它们不表达同一事实。 |
| “时长不等于 30”会包含未知吗？ | `duration_minutes != 30` 不包含 NULL；若业务还要待确认项，写 `duration_minutes != 30 OR duration_minutes IS NULL`。 | 先决定未知行要不要进入答案，再写条件，不把未知自动当成“不等于”。 |
| 怎样查完整的一天？ | `starts_at >= 起点 AND starts_at < 次日起点`，包含起点、不包含次日零点；`BETWEEN 30 AND 45` 则包含两个端点。 | 认熟时间范围与数值闭区间的差别。日期文字直接比较，前提是有效日期、统一格式与时区含义。 |
| 精确匹配和模糊匹配怎么分？ | `status = 'open'` 精确比较；`note LIKE '%确认%'` 找包含“确认”的文字；LIKE 中 `%` 匹配零到多个字符，`_` 匹配一个。 | 逐渐用熟当前常用模式；LIKE 不是完整正则表达式，NULL 备注也不会因此匹配。 |
| AND、OR 混在一起，为什么多选了旧预约？ | `AND` 比 `OR` 先结合。用 `(status = 'open' OR status = 'pending') AND 日期条件`，让日期限制两类状态。 | **把“哪些要求一起成立”写清楚。** 括号表达业务分组，不靠从左到右猜。 |

原章时间均按统一格式保存，才有文字顺序与时间顺序一致的条件。混用日期格式、不同偏移量或无效日期时，先统一输入约定；不能只看列叫 `starts_at` 就认为可以正确排序。

回看：「“没有备注”为什么不能写成普通相等比较？」「查一天、找一种文字，条件又怎样选？」。

### 要一条条列出，还是把它们算成一个答案？

| 当前问题 | 关系或短用法 | 记到什么程度 |
|---|---|---|
| 数预约和数已知时长，有什么不同？ | `COUNT(*)` 数行；`COUNT(duration_minutes)` 数非 NULL 时长。对 `30、60、NULL`，分别为 3 和 2。 | **计数对象要明确。** 有三条预约，不代表知道三条的时长。 |
| 总工时和平均工时包括未知吗？ | 本例 `SUM`、`AVG`、`MIN`、`MAX` 忽略 NULL；`30、60、NULL` 得到已知总量 90、已知平均 45。 | 能解释统计口径；90 不是这三条的完整总工时，平均值也不是擅自补零后的 30。 |
| 聚合后的一行代表谁？ | 不带 GROUP BY 的这条聚合把所选记录合成一行统计；不能随意加一个客户名，指望它代表整组客户。 | **结果的一行已从“一条预约”变成“这组记录的统计”。** C02 再处理每组一行。 |
| 只要有哪些类型，用什么？ | `SELECT DISTINCT service_type ...` 去掉相同结果行；选两列时，对两列的完整组合去重。 | 认熟 DISTINCT 的去重对象；它不计数，也不是修补错误查询的通用办法。 |

筛选后没有行时，不带分组的这类聚合仍给一行统计：`COUNT` 为 0，其余上述聚合为 NULL。先分清“没有记录”“未知值”与“已知值确实是零”，再解释数字。

完整六行夹具与 `query_lab.py` 查用即可。`connect(':memory:')` 的库随连接关闭消失；循环从 `execute(sql)` 取得的每个元组对应一条结果行。这个实验核对查询含义，没有证明重启后数据仍在。

回看：「从“列出预约”变成“估算总工时”，结果的一行变了什么？」「只是想知道有哪些服务类型，需要统计吗？」「想亲自核对时，用一个不会留下数据库文件的实验」。

## C02｜多张表怎样组成一个答案，又为什么多了或少了行？

本章的问题是“具备电气技能的人，下周各有多少预约，零预约的人也要出现”。沿着**找到合格的人 → 接上周内预约 → 每人汇总一行**，始终问：当前结果一行代表什么？

### 是找名单中的人，还是把两边信息放在一起？

| 当前问题 | 关系或短用法 | 记到什么程度 |
|---|---|---|
| 客户名字为什么不直接写进每条预约？ | `appointments.customer_id` 指向 `customers.id`；客户改名仍是同一个身份。一位客户可以对应多条预约。 | **身份与属性分开。** 主键标识本表行，外键约束引用；表名相近不会自动建立对应。 |
| 一个人多项技能，一项技能又属于多人，怎样表达？ | `technician_skills` 每行保存一对 `(technician_id, skill_id)`。 | 看懂多对多经中间表拆成关系行；不用增加无穷的 `skill1`、`skill2` 列。 |
| 只问某人是否属于合格名单，需要接出全部技能列吗？ | `WHERE id IN (SELECT technician_id FROM ...)` 让子查询提供编号集合，外层判断成员。 | 逐渐认熟“取得一组值 → 判断属于其中”；这是逻辑含义，不承诺引擎建立临时表。 |
| 预约旁要显示客户姓名，怎样组合？ | `JOIN appointments AS a ON a.customer_id = c.id`，配合 `c.name`、`a.id` 选两边的列。 | 用熟别名、列来源与 ON 对应关系；**JOIN 决定本次组合，外键决定哪些引用允许保存。** |
| 客户姓名出现两次，就是重复数据吗？ | C1 分别匹配 A1、A3，会有两行“预约及其客户”。漏写对应条件，两客户与四预约却会形成八个组合。 | 先看每行含义及匹配次数；正常一对多会展开，错误 ON 要修关系，DISTINCT 不能恢复归属。 |

本章客户、技术员编号直接在预约表上。C03 会引入独立的工单和时段，查询路径也随之改变；这两套结构不能直接拼成同一份库。

回看：「先把分散的事实摆在一起」「先只找人：为什么可以把一条查询放进另一条？」「JOIN 怎样让客户姓名出现在预约旁边？」。

### 怎样保留没有预约的人，再正确数成零？

| 当前问题 | 关系或短用法 | 记到什么程度 |
|---|---|---|
| 有空的技术员为什么从结果消失？ | INNER JOIN 只留匹配组合；`LEFT JOIN appointments AS a ON ...` 在右侧没有匹配时仍保留左行，右列补 NULL。 | **是否必须保留左侧对象，决定连接方式。** 此处 NULL 表示没有匹配，不是某条预约忘填了编号。 |
| 改了 LEFT JOIN，零预约的人还是没了？ | 限定右表周内预约的日期条件放 ON，决定“哪些预约能配”；放 WHERE 则会把右列为 NULL 的占位行筛掉。 | 分清匹配条件与连接后的筛选；LEFT JOIN 不保证后面的 WHERE 继续保留左行。 |
| 怎样从预约明细变成每人一个数量？ | `GROUP BY t.id, t.name`，再 `COUNT(a.id)`；本例 T1 的 A1、A2 得 2，T2 的 NULL 得 0。 | 逐渐用熟按身份分组、数真实预约主键；只按姓名可能合并同名人。 |
| 为什么 COUNT(*) 把空闲者数成 1？ | 它数的是左连接留下的占位行；`COUNT(a.id)` 只数非空预约编号。 | **先说要数什么，再选计数列。** 不能见到“行数”就一律使用 COUNT(*)。 |
| 只显示预约至少两条的人，在哪筛？ | `HAVING COUNT(a.id) >= 2` 筛形成后的组；WHERE 决定哪些输入行参与分组。 | 认熟“统计前选记录”与“统计后选组”；HAVING 片段需放进完整查询，不是独立 SQL。 |

最容易丢失的关系可以缩成：

```text
T1 匹配 A1、A2 → 两条明细 → COUNT(a.id) 为 2
T2 没有匹配   → 一条占位 → COUNT(a.id) 为 0
```

LEFT JOIN 的完整 ON 同时包含技术员对应和周内时间范围。含技能筛选的最终多表查询查原章即可；要认得日期限定预约匹配，而 `WHERE s.code = 'electrical'` 仍用于选合格技术员。

回看：「为什么有空的技术员反而不见了？」「怎样从两条预约，得到“王玥有两条”？」。

### 数量变大，是关系展开还是需要合并名单？

| 当前问题 | 关系或短用法 | 记到什么程度 |
|---|---|---|
| 两项技能、两条预约，为什么数出 4？ | 同时接上两个一对多分支，得到“每项技能 × 每条预约”的四个组合；表里没有新增预约。 | **先找哪一层放大了组合。** 只需技能资格可先用 IN 筛人；确实要不同预约数才用 `COUNT(DISTINCT a.id)`。 |
| DISTINCT 能代替 GROUP BY 吗？ | 只选技术员列并 DISTINCT，可列不同的人；保留预约编号则 A1、A2 本来就不同。两种都没有自动算预约数。 | 按“名单、明细、统计”选择结果形状，不把去重当汇总。 |
| 两份编号名单怎样并、交、减？ | UNION 合并并去重；INTERSECT 留共同成员；EXCEPT 留左边有而右边没有；UNION ALL 保留重复。 | 先能区别**组合同形状答案**与 JOIN **关联事实**；少用关键字按需查，EXCEPT 的左右顺序有意义。 |

集合操作两侧应交出数量一致、业务含义可比较的列。完整 SQLite 夹具见原章 `relation_lab.py`；其中 `PRAGMA foreign_keys = ON` 是本次连接的规则开关，查询本身不会替它开启。

回看：「多对多连接为什么也会放大数量？」「两份名单要合并或求交集时，还是 JOIN 吗？」「把这些已知行交给 SQLite 核对」。

## C03｜怎样让坏数据进不来

C01、C02 判断答案；C03 反过来设计**事实放哪里、怎样对应、哪些坏状态不能保存**。约束能保护写入入口，但不会替应用补齐所有业务判断。

### 哪些事实需要独立身份与保存位置？

| 当前问题 | 关系或短用法 | 记到什么程度 |
|---|---|---|
| 本章预约怎样找到客户和技术员？ | 客户经工单找到，技术员经时段找到：`customers ← tickets ← appointments → slots → technicians`。箭头从引用行指向被引用行。 | **能沿真实外键追事实。** 工单未预约、时段未被选择时也能独立存在，不照抄前章的小表列。 |
| 主键和外键各保护什么？ | 主键让 ID 唯一确定本表行；`customer_id REFERENCES customers(id)` 要求非空引用找到目标客户。 | 姓名可重名和改变，不能替代这里的稳定身份；C999 失败是目标不存在，不是编号格式不对。 |
| 多对多为什么用组合主键？ | `PRIMARY KEY (technician_id, skill_id)` 拒绝重复 `(T1,S1)`，仍允许 `(T1,S2)` 与 `(T2,S1)`。 | 认熟“唯一的是一对关系”，不误读成每个技术员只能出现一次。 |
| 规范化在这里实际解决什么？ | 客户当前邮箱在客户表，技能名称在技能表；其他行通过身份找它，减少同一事实多处更新的矛盾。 | 能解释拆表理由；历史发信所用地址是另一种事实，不该冒充当前邮箱，也不必把每个文字都拆表。 |

完整七表 `c_schema.sql` 的价值在共同表达这些关系。表名与全部列无需背诵；需要改结构时，先找独立对象和引用方向，再查看整份 schema。

回看：「一张预约究竟连接了哪些事实？」「数据库怎样发现 C999 根本不存在？」「技能为什么还需要一张关系表？」「把这些决定放在一起，表应该怎样建？」。

### 哪一种坏值，应由哪条规则拒绝？

| 当前问题 | 关系或短用法 | 记到什么程度 |
|---|---|---|
| 写了 INTEGER，为何仍收到文字或负数？ | 普通 SQLite 表有类型亲和性；`'60'` 可转成整数，`'thirty'` 可留下 text，负数也是整数。 | **类型声明与业务规则分开。** `typeof(列)` 可看存储类别；不由列名或声明推断原始输入类型。 |
| 时长必须是正整数，怎样表达？ | `INTEGER NOT NULL CHECK (typeof(duration_minutes) = 'integer' AND duration_minutes > 0)`。 | 能指出非空、存储类别、正数各守哪一处；完整建列写法查用。转换后的 `'60'` 仍能通过。 |
| 必填、唯一、范围与真实引用如何分工？ | NOT NULL 拒绝缺值；UNIQUE 拒绝重复；CHECK 检查表达式；外键检查对应目标。 | 逐渐认熟并按坏值定位，不能用其中一个替代其余。单独 UNIQUE 不拒绝多个 NULL。 |
| CHECK 和默认值为什么补不出可靠事实？ | CHECK 结果为 NULL 时不算违反，因此必填仍需 NOT NULL；DEFAULT 处理省略列，不会把显式 NULL 自动变成初值。 | **未知电话保留 NULL，确定的初始状态才用默认值。** 普通文字主键也按本章显式加 NOT NULL。 |
| 一个时段最多一条预约，是外键保证的吗？ | `slot_id` 外键保证时段存在，UNIQUE 限制它最多被一条预约引用；取消历史也在唯一范围内。 | 认清“存在”与“数量”是两条规则；此模型没有自动支持取消后复用时段。 |
| 开启了约束，就能保证日期和联系信息可靠吗？ | 日期 TEXT 非空未验证日期、营业时间或重叠；电话长度不证明能拨通；技能表也未证明本次匹配正确。 | 看实际表达式承诺的范围；日期解析、邮箱规范化、权限和技能匹配仍需应用明确处理。 |

SQLite 外键开关属于每条连接。需要在事务外设置 `PRAGMA foreign_keys = ON`，再用 `PRAGMA foreign_keys` 读回 1；只在建库时开过一次，不保证以后新连接也检查。完整连接设置可以查，**必须实际启用**的关系不能漏。

`ON DELETE RESTRICT` 保护被引用的一端：仍有工单引用 C1 时，不允许删掉 C1。C04 会把它与取消和级联删除联系起来。

回看：「数据库怎样发现 C999 根本不存在？」「一列写着 INTEGER，为什么还能收下文字？」「哪些事实必须有值，哪些未知应该留下？」「把这些决定放在一起，表应该怎样建？」。

### 规则写下了，怎样判断已有数据真的受保护？

| 当前问题 | 关系或短用法 | 记到什么程度 |
|---|---|---|
| 出现约束错误，证明到哪一步？ | 坏值应在预期规则处被拒绝，还要读回或比较状态，确认没有留下新行。 | 查用种子和验证程序，理解错误类别与数据结果；极小合成库的 `iterdump()` 比较不能照搬为真实业务日志。 |
| 修改 CREATE TABLE 文件，会更新旧库吗？ | 不会；它只改变以后怎样建表。迁移要让旧结构与旧行一起进入新规则。 | **改定义文件与迁移已有数据库分开。** 新增可空列时，旧记录不知道的新事实仍可为 NULL。 |

### 语句执行、错误拒绝与整组提交，差在哪？

| 当前问题 | 关系或短用法 | 记到什么程度 |

| 新增、修改和删除分别用什么？ | INSERT 新增行；`UPDATE ... SET ... WHERE ...` 修改符合条件的行；DELETE 移除行。 | 逐渐认熟动作与目标条件；更新或删除不能漏掉本来需要的 WHERE。 |

## C05｜应用怎样安全读到预约，并留下能追踪的线索

本章把关系接回应用：**客户参数 → 固定查询 → 当前结果行 → Python 字典列表 → 调用者使用**；旁边用一次处理的标识、结果与耗时记录运行线索。它采用独立读取库，客户和技术员编号直接在预约表上。

### 哪个库、哪些行、谁交回值，是三件什么事？

| 当前问题 | 关系或短用法 | 记到什么程度 |
|---|---|---|
| 查不到数据，先核对文件还是客户编号？ | 数据库路径决定打开哪份库；客户参数决定在该库中选哪些行。 | **访问目标与查询条件分开。** 改客户编号不能补回缺失的表或 view。 |
| 看板为什么恰好是 A-11、A-13？ | JOIN 接上客户和技术员，筛 C-1 且排除 cancelled，再按时间和预约 ID 排序。 | 能沿真实主键匹配、条件与顺序解释两行；每行仍是一条预约，组合结果没有写回底表。 |
| engine、connection、execute 各做什么？ | `create_engine(...)` 建立连接管理入口，通常延后实际连接；`with engine.connect()` 取得本次连接；`connection.execute(...)` 执行。 | 认熟创建入口、取得连接、执行查询三个动作；URL 配置不等于查询已发生。 |
| `text()`、Result、字典列表能混为一谈吗？ | `text(SQL)` 包装可执行语句；execute 返回 Result；`mappings().all()` 按列名取得全部行；`dict(row)` 转成普通字典。 | **语句 → 执行结果 → 应用值**的方向要清楚。text 不读库，修改返回字典不会自动改表。 |
| with 结束，是不是每次都关掉全部数据库连接？ | 离开 connect 块释放本次使用并结束未提交事务；底层连接可能归池复用。整个实验收尾用 `engine.dispose()` 释放当前空闲连接。 | 能解释用完归还，不用背连接池参数。取完小结果再返回；巨大结果另查分页或分批。 |

已有 `CUSTOMER_QUERY` 和 `engine` 时，常用交接片段是：

```python
with engine.connect() as connection:
    result = connection.execute(CUSTOMER_QUERY, {"customer_id": customer_id})
    rows = [dict(row) for row in result.mappings().all()]
```

`return rows` 再把列表交给调用者。代码不需要先建立 ORM 类；本章使用 SQLAlchemy Core。SQLAlchemy 里的 `:customer_id` 与 sqlite3 小例里的 `?` 都是值的位置，完整写法随实际入口查。

初始化、锁定依赖与 `make_engine` 回调是长配方，查原章相邻完整程序。关键关系是：SQLite 外键要在**每条新底层连接**、事务外启用并读回；初始化时开过不够。本章初始化用 `autocommit=True` 管固定脚本，应用用 `autocommit=False`；不要把两处配置混成同一模式。示例 `c05_setup.py` 仅首次建新文件，反复读取不用重复初始化。

## C06｜结果对了以后，怎样判断慢在哪里

本章的线索是：**固定正确答案 → 看数据库的访问计划 → 在相同条件下重复计时 → 判断收益是否值得维护成本**。计划和耗时回答不同问题，都不能替查询判断客户、行与顺序是否正确。

### 怎样先固定这次要比较的工作？

| 当前问题 | 关系或短用法 | 记到什么程度 |
|---|---|---|
| 日志报一次慢，就能确定数据库有问题吗？ | 先找同类 operation 的重复现象，按 request ID 对上处理；总计时可能含连接和结果整理。 | 先认范围与稳定性，不把一个样本当结论。取有代表性的数据、输入与 SQL 复现。 |
| “最近 20 条”为什么只验行数不够？ | `WHERE customer_id=? ORDER BY starts_at DESC, id DESC LIMIT 20`，同时约定客户、先后与并列次序。 | **比较的是正确完整行及顺序。** 20 行仍可能属于错误客户或拿错边界。 |
| 错误 JOIN 很快，能开始优化吗？ | `ON c.id=c.id` 没约束预约归属，两客户与三预约变六行；先改 `ON a.customer_id=c.id`，再建立正确查询的基线。 | 先修结果含义；DISTINCT 和索引都不能为错误对应作担保，错误 SQL 的旧耗时也不是正确基线。 |

在本章独立四列表中，目标客户有 30 条；约定答案是 `100030` 到 `100011`，同日的 `100030` 在 `100029` 前，状态不排除任何一条。这个固定结果用来比较前后，样例编号不需要记。

回看：「“最近 20 条”究竟应该是哪 20 条？」「如果结果数量本来就错了，应该先改哪里？」。

### 索引改变了哪一段工作，计划能说明到哪里？

| 当前问题 | 关系或短用法 | 记到什么程度 |
|---|---|---|
| 怎样看数据库准备怎样查？ | 在同一 SELECT 前加 `EXPLAIN QUERY PLAN`；保持查询与参数一致，读表名、索引名和使用条件。 | 逐渐认熟计划入口；它描述访问路线，不是实际耗时，也不是业务正确性判定。 |
| SCAN 是错误，SEARCH 就一定快吗？ | SCAN 表示遍历路线，也可能沿索引；SEARCH 表示按条件定位部分行。 | **结合具体对象与条件解释**，不把英文词当成绩；输出格式随 SQLite 版本可能变化。 |
| 按客户建索引，为何排序仍在？ | 本例单列索引帮助定位目标客户的 30 条；它没有保证完成 `starts_at DESC, id DESC`，所以仍可能有 `USE TEMP B-TREE FOR ORDER BY`。 | 看懂“少访问无关行”与“减少排序”是不同收益。出现临时排序不等于客户索引没作用。 |
| 索引是另一份业务表吗？ | `CREATE INDEX idx_appointments_customer_id ON appointments(customer_id)` 建立随原表维护的查找结构；应用仍发同一 SELECT。 | 认熟“为哪张表、哪列提供路线”；不是新增预约，也不需把 SELECT 改查索引名。 |

完整前后计划与重复计时代码查原章 `c06_history.py`。索引只是具体候选；是否采用及有多少收益，由当前计划和实测回答。

回看：「表里另外有十万条预约时，它怎样找到这位客户？」「计划变了，怎样知道这次改变有没有用？」。

### 数字更小，怎样判断是否值得保留？

| 当前问题 | 关系或短用法 | 记到什么程度 |
|---|---|---|
| 两边计时怎样才可比较？ | 相同 SQL、参数、数据、取行范围、预热和重复次数；每轮确认完整结果相同，保留原始样本。 | 先守同一工作与口径，再比较数字；不能一边只计 execute，一边计到取完行。 |
| 中位数能排除所有波动吗？ | median 减少极端值对代表值的影响，但不表示最慢请求，也不消除缓存和后台负载影响。 | 认熟代表值的用途和边界；差异与波动相当时，结论是当前收益不明确。 |
| 小表、少数不同值，就一定不需要索引吗？ | 看当前条件实际匹配多少行，也就是缩小范围的能力；少数状态中某一个很稀少，仍可能有收益。 | **选择性联系当前输入与分布。** 不只数不同值，也不背“每列都建／某类永远不建”。 |
| 读得更快，代价在哪里？ | 索引占空间；新增、删除行或修改索引相关列需维护条目。结合读取频率与写入负担判断。 | 有收益才考虑保留；本章内存读取实验没量化磁盘空间、写入成本或整次 HTTP 等待。 |
| 换回 C03、C04，也照抄这个索引吗？ | 那里的预约经 tickets 找客户，没有本章直接的 `appointments.customer_id`；需拿实际 JOIN、过滤、排序重新解释和测量。 | **迁移的是判断方法，候选必须服从真实结构。** 同名业务问题不保证同一 SQL。 |

本章计时包含执行查询并 `fetchall()` 取完结果，不包含建库、生成数据、创建索引、断言和 JSON 输出；不能与 C05 含连接使用的事件耗时直接相减归因。它使用源码说明的 sqlite3 旧式事务控制写法，也不是 C04 显式 SQL 事务的替代模板。

多列、覆盖、部分索引，在单列方案后仍有明确瓶颈时再查；两连接争用要回到事务、锁与受控复现；空间回收才考虑 VACUUM。这些都不是遇到慢查询就执行的一套命令。

回看：「计划变了，怎样知道这次改变有没有用？」「索引读得快一些，就应该留下吗？」「回到完整应用时，哪些结论可以带走？」。

读到这里可以把 C 册重新接成一个判断：**事实由哪里保存，结果一行代表什么，成功必须共同留下哪些状态，失败后能凭什么证据继续。** 全套配套的 schema 与接口以它自己的文件为准；需要整体验证时，再回看「运行之前，先知道会改变什么」与「怎样知道不是只把测试运行了一遍？」。

下一册遇到外部供应商时，本地 ROLLBACK 不能自动撤回对方已经执行的动作。数据库的提交边界明确以后，才有依据继续判断外部失败、等待和重复请求。
