# X 册｜章节记忆与查用

这份表帮助把 A–F 的关系放回同一套应用：当前交出了什么，谁接手，哪些事实已经保存，下一项证据应该去哪里找。按遇到的交接查，不把前六册再背一遍。

**关系要能解释，常用操作逐渐用熟，长配方带着目的查。** X01 追创建与另一条政策请求；X02 判断失败前已经发生什么；X03 组织证据；X04 核对实例替换、恢复与交接。四章是在观察同一系统，不是四个依次经过的服务。

**表里的跨层英文名先看它连接的责任、状态和证据。** 文件名、脚本名、字段名和状态码只是查找锚点；先能沿输入→处理→持久事实→公开结果走通，再回头认熟具体名称。

这里有两个独立的数据所有者：应用保存工单与事件，模拟合作方保存派单 receipt；本地事务不能把二者一起撤回。Fake Model 的政策草稿又是另一种结果，它不自动成为工单事实或动作权限。

X 使用自己的空基线和数据库。T-42 不与其他册共用记录，D/E 的 LOCAL-0042 也不能直接替换它。配套客户端是 Python 程序，没有已实现的网页。所有编号、地址、D1/C1/B1 和输出均为示例或代号，不是当前电脑的实测结果。

下文“回看”指 X 册原教材的同名小节；明确标出其他册时再回相应教材。从可见入口 `02_配套代码_F与综合应用/examples/x_cross_layer/support-ticket-system` 复制完整项目，再在自己的实验副本中查 `RUNBOOK.md`。它与底层 `02_配套练习_FX新版` 指向同一份配套，不是另外一套实验。准备条件与完整环境命令见原教材「先读关系，想运行时再准备实验副本」；本资料不要求安装或运行，也不把阅读当作运行验证。

## X01｜一张工单怎样从文字变成可以读回的事实？

抓住三次关键交接：**输入变成 API 可用值；第一笔事务把本地意图保存；合作方确认再交给第二笔事务。** 最后一次 GET 读到的是已经提交的状态，不是客户端仍握着的同一个对象。

### 从文字到数据库，哪一步才留下工单？

| 当前问题 | 关系或短用法 | 记到什么程度 |
|---|---|---|
| 输入 `"3"` 后，何时能发请求？ | `strip()` 清理边缘空白，`int()` 转整数，再查 1–3 范围；`urgent` 在转换失败，`-3` 在范围失败，都不进入 HTTP 调用。 | 把 A 册的值流接到 B 册请求入口；先分清“没发出”和“发出后被拒绝”。 |
| 客户端 dict 怎样交给 API？ | HTTPX 的 `json=` 编成 JSON 请求体；接收方从字节解析自己的对象。 | **两端数据表示相通，内存对象不共享。** 编码本身不证明服务接受。 |
| 客户端检查过，API 为何还校验？ | 任意调用者都可绕过该客户端；X 的 `TicketCreate` 要求 priority 严格整数 1–3，拒绝额外字段等。 | 本例 `"priority":"3"` 返回 422；不能照搬其他示例允许转换的规则。 |
| `validation_passed` 表示工单已保存吗？ | 只说明输入成为 API 可用对象；随后还需核心数据条件检查与创建事务。 | **合法输入与持久事实分开。** |
| 第一笔事务一起保存哪些事实？ | tickets 行含工单、create_key 与输入摘要；ticket_events 保存创建事件；编号计数同时前进，最后 COMMIT。 | 认清一个事务的共同边界；本例没有单独的幂等记录表。 |
| 事件 INSERT 失败，工单与编号怎样变化？ | 本例事务失败时一起撤回：无新票、无新事件，下一编号仍是 42。 | 票、依据与编号要共同成立；失败前打印日志不能替数据库提交。 |

`BEGIN IMMEDIATE` 在 SQLite 事务开始时申请写事务；完整函数与 SQL 查原章，不在表里拼写入配方。回看：「同一个 3，怎样离开客户端进程？」「客户端已经检查过，API 为什么还要检查？」「第一笔事务为什么同时保存工单、意图和事件？」。

### 本地已保存，为什么还要经过外部确认和第二笔事务？

| 当前问题 | 关系或短用法 | 记到什么程度 |
|---|---|---|
| T-42 为什么同时 open 和 pending？ | open 表示工单仍待处理；assignment_status=pending 表示派单确认尚未在本地收束。 | **工单状态与派单状态直接分清。** 有票不等于已有安排。 |
| 工单创建 key 与 `assignment:T-42` 标识同一动作吗？ | 前者识别本地创建意图；后者识别合作方派单意图。request ID 则关联本次处理。 | 稳定意图、外部意图、本次请求分开，不能互换字段。 |
| 派单请求把全部工单交出去吗？ | 本例 body 只含 ticket_id、device_id；另带 Idempotency-Key 和 X-Request-ID header。 | 按交接用途认字段范围；不发送 subject/priority 不等于没带关联头。 |
| 等待合作方时，还持有创建事务吗？ | 第一笔事务已提交，之后才发网络请求；本地没有持有写事务等回复。 | 能解释为什么后来 timeout 不能跨网络撤销对方效果。 |
| 合作方返回 PA-1，本地就 confirmed 了吗？ | adapter 先核 HTTP、JSON 和字段；`finalize_assignment()` 再用第二笔事务保存确认与 assignment_confirmed 事件。 | **收到可用外部结果，不等于本地已持久化。** |
| partner_confirmed 为什么不等于工单关闭？ | 派单确认后工单仍 open；有人安排处理不代表故障修好。顶层确认标记从已保存的派单状态推导。 | 公开结果要依据已提交状态，不依据打算或刚收到的候选回复。 |
| GET T-42 会重新派单吗？ | 它查询本地行并返回公开工单，不调用合作方或模型。 | 认清只读交接；创建 response 与后续 GET 要能对上。 |

三个“状态”可同时成立：HTTP `201` 是本次创建结果，工单 `open` 是故障处理状态，`partner_confirmed` 是派单子流程状态。数据库物理列叫 `status`，API 映射为 `ticket.ticket_status`；改公开名称没有改变存储所有者。

回看：「open 与 pending 为什么会同时成立？」「合作方确认以后，为什么还要第二笔事务？」。

### 政策请求交回的是什么，为什么不能替工单作决定？

| 当前问题 | 关系或短用法 | 记到什么程度 |
|---|---|---|
| 创建以后，政策草稿是自动附带的下一步吗？ | 处理人员另发 `POST /tickets/T-42/policy-draft`，用新的 request ID；应用读工单和获准资料，再请求 Fake Model。 | 两项任务分别发起；草稿分支不是创建事务的一部分。 |
| “用户报告离线”和“政策要求确认离线”一样吗？ | 前者是工单报告，后者是行动前条件；两者都不证明设备已检测或当前配置已备份。 | **描述、要求与已经完成的事实分开。** |
| `accepted_draft` 允许直接执行恢复吗？ | 应用检查结构、引用和本例窄政策条件后，交回可供人核对的草稿；不写成工单完成事实。 | 候选被接受的用途是草稿，不自动获得动作权限。 |
| 没有资料、引用不属于本次资料，各停在哪里？ | 无适用资料则 abstained，模型调用为零；引用越界则 needs_human。 | 先判依据是否存在，再判候选能否采用；HTTP 200 不保证候选可用。 |
| 模型建议 `close_ticket`，谁决定能否调用？ | 本应用只有 `ticket:read` 权限，返回 needs_human / tool_permission_denied；tool calls/effects 都为 0，工单仍 open。 | **模型建议与应用授权分开。** 拒绝后还需看调用和状态证据。 |
| Fake 检查通过，能说明真实模型可靠吗？ | 本例检索是封闭资料筛选，claim 检查是固定文字条件，Fake 提供受控候选。 | 只能验证本例检查位置与规则；真实资料和模型效果回 E 册另做评测。 |

回看：「另一个请求为什么只产生草稿？」。完整关系 trace 入口是 `walkthrough.py success`，见「看见同一程序里的这些交接」：它新建临时 SQLite，TestClient 进入真实 API，HTTPX MockTransport 接住外部边界，结束后清理临时数据。其创建 201、重放 200 和计数是受控实验预期，尚未经过真实监听端口。

## X02｜同样返回 503，为什么处理方式不同？

失败后先恢复三个位置的事实：**本地是否提交、外部是否已生效、公开 response 表达哪一段失败。** 状态码相同不能抹掉这些差异。

### 同样的 503，停在第一笔事务之前还是第二笔事务旁边？

| 当前问题 | 关系或短用法 | 记到什么程度 |
|---|---|---|
| `write-blocked` 的 503 前发生了什么？ | 输入通过，必要数据库读取被锁阻塞；记录 ticket_write_precondition_failed，尚未进入 create_intent。 | 这是创建前条件失败，不能称作本次事务内 rollback。 |
| 怎样证明这次还没有本地或外部效果？ | 释放实验锁后核对正确数据库：tickets=0、next=42；同时 provider calls/effects=0。 | **缺 commit 日志不足以独立证明未写入。** 还需持久状态与调用证据。 |
| 条件恢复后，可以怎样再尝试？ | 本项目这条失败允许相同创建 key 与完全相同 payload 再试；没有旧意图时仍创建该实验的 T-42。 | 规则来自已定位的程序行为，不推广成“任何 503 都能安全重试”。 |
| `assignment_result_not_persisted` 又是什么情况？ | 第一笔事务已保存 T-42/open/pending，合作方已有 PA-1，第二笔事务未保存确认，因此返回 503。 | **客户端失败、本地有票、远端有结果可以同时成立。** |
| pending 怎样继续，而不另建一张？ | 换 request ID，保留原创建 key/payload，找到旧 T-42；再以原 assignment key 取得 PA-1，完成第二笔事务。 | 继续原有交接，不把未知结果改成新意图。 |
| 恢复后两次 provider calls，是否重复派单？ | 本例最终 calls=2、effects=1，一张票 confirmed，返回 200 与 replayed=true。 | **调用次数和效果次数直接分清。** 二次调用可以是在取回一次已完成效果。 |

两条演示各自从空临时数据库开始，不共享 T-42。完整受控故障入口 `walkthrough.py write-blocked`、`walkthrough.py pending-recovery` 回看「第一种 503：连本地创建都没开始」「第二种 503：工单与合作方结果都已存在」。它们会在临时实验中制造锁或保存失败，不是修复当前真实数据库的命令。

X 按自身不可变工单字段、create_key 与摘要恢复受限派单；不能称为 D 册版本化 canonical payload 合同已原样照搬。

### 外部没确认，为什么 202 可能是诚实的降级结果？

| 当前问题 | 关系或短用法 | 记到什么程度 |
|---|---|---|
| 合作方连续 500，本地工单也失败了吗？ | 本地票已提交；有限尝试后，第二笔事务一起保存 manual_review、人工接管行与事件。 | 保存工单的最低目标可成立，自动派单目标仍未完成。 |
| 202 的公开字段怎样读？ | `local_saved=true`、`partner_confirmed=false`，有人工接管记录。 | **降级事实要明确表达，不能把 manual_review 当 confirmed。** |
| 对已收束的 manual_review 重放，会再试合作方吗？ | 本例只读回旧意图，不重新消耗一轮重试预算；返回 200。 | 先看旧状态是否已收束，不把所有重放都当重新调用外部。 |
| 两次尝试和预算意味着绝对墙钟上限吗？ | 每次前重算剩余预算，限制 timeout/退避并停止后续尝试；HTTPX timeout 仍分连接、读、写、连接池阶段。 | 分清调度预算与正在进行的 I/O；不能声称底层累计绝不超时。 |
| timeout 能证明对方没创建吗？ | 它表示某阶段没及时得到结果，对方可能已经生效；500 则是已收到的一份回应。 | **结果未知不等于无效果。** 核对原派单意图，不盲目换新 key。 |

完整降级 trace `walkthrough.py degraded` 预期为创建 202、重放 200、calls=2、effects=0 和一条人工接管记录。这只对应受控的 always-500 场景，不能把其 effects=0 套到所有 timeout。回看：「外部失败为什么有时返回 202？」。

### 从手里已有的现象，怎样选下一处检查？

| 当前问题 | 关系或短用法 | 记到什么程度 |
|---|---|---|
| 输入 urgent，客户端直接报错？ | 先看转换入口与当前文字；HTTP 调用为零时尚未请求 API。 | 从最早已知偏离定位，不先查数据库。 |
| HTTPX ConnectError，没有 response？ | 核对本次 URL、端口、监听与服务端接收情况。 | 传输异常不是一个凭空存在的服务器 500。 |
| body 中 priority 是字符串，返回 422？ | 对照本次请求字段与 X 的严格输入合同。 | 已有输入证据时，不先改索引或重试策略。 |
| 本地 pending、对方有 receipt，却返回 503？ | 找第二笔事务、稳定意图与 receipt，核对确认是否保存。 | 把错误接回未完成交接，不删除已存在的票。 |
| 政策 response 200，但 needs_human？ | 核对业务 reason：例如 citation_not_retrieved 或 tool_permission_denied；检查工单不变与工具为零。 | **HTTP 成功交回拒绝结果，不等于候选被采用。** |
| live 成功，ready 返回 schema 失败？ | X 的原因为 `schema_version_mismatch`；核对 expected/actual。F 独立应用可能叫 `schema_mismatch`。 | 共通关系可复用，示例原因码不能互换。 |

收集顺序可以从客户已有的 response 开始，再沿 request ID 向前找最后成功与首次偏离；不要求从源码第一行查起。先保留输入形状、目标、公开原因和持久事实，再选择会改变现场的重启或配置动作。回看：「先判断有没有请求，再判断请求停在哪里」「另一条分支失败，会不会改变已经保存的工单？」。

## X03｜怎样证明重放没有多建一张工单？

本章只围绕一项承诺选证据：**同一 key 与同一输入重放，取回原工单，不增加已经完成的业务效果。** response、数据库、外部计数和日志各补一段，不能互相替代。

### 第二次传送，怎样仍然指向第一件事？

| 当前问题 | 关系或短用法 | 记到什么程度 |
|---|---|---|
| 哪个值要稳定，哪个值应换新？ | 创建 key 与业务 payload 保持，request ID 区分第二次处理；201→200，replayed 从 false→true。 | 能同时表达“一件事”和“两次传送”；它们都不是用户身份或权限。 |
| 同一 key 携带不同主题会怎样？ | 本例对照规范化 payload 摘要，不同返回 409，原行不变。 | **重放不等于借旧 key 修改原意图。** 先判断是修改工单还是新业务动作。 |
| 所有重放都不能增加外部 calls 吗？ | 已收束 confirmed/manual_review 直接读回；pending 可能继续交接，calls 增加但 effect 不应重复。 | 根据先前状态选预期，不把正常重放的计数当全局规则。 |

回看：「两次请求怎样指向同一件事？」。

### “没有重复”需要哪几份互补证据？

| 当前问题 | 关系或短用法 | 记到什么程度 |
|---|---|---|
| 两次 response 都是 T-42 就够吗？ | 比较 201→200、replayed 标记以及全部公开工单字段，之后 GET 还应一致。 | 证明公开合同；仍可能藏有重复数据，需要数据库核对。 |
| 本地查一张票，还要看创建事件吗？ | 正常重放预期 tickets=1、ticket_created=1；防止重复持久化或记录来源不一致。 | 数据与事件共同核对，不只看返回的编号。 |
| provider calls/effects 解决哪个疑问？ | 正常已收束重放都维持 1；pending 恢复可为 2/1。 | 本地一张票不保证远端只有一项安排；计数含义依场景。 |
| 第二次日志能补什么？ | 正常重放应有 ticket_intent_replayed，不再走新的 commit/partner 事件链。 | 说明控制路径；没有日志仍不能单独证明没有效果。 |
| 查到一行，怎样确认是这次应用的数据？ | 核对数据库文件/连接目标和环境；旧副本的查询结果不说明当前 API。 | **查询对象身份与查询内容同样重要。** |

直接查物理列时，认熟 `status AS ticket_status`：前者是本例数据库列，后者只是结果别名；没有新增或重命名表中字段。按 `WHERE ticket_id = :ticket_id` 绑定目标编号，完整 SELECT 回看「SQL 查询为什么还要关心物理字段名？」。

组合断言程序 `x03_replay_check.py` 回看「用一段可运行实验把这些断言接在一起」；它使用临时真实 SQLite 与有状态 Fake，核对票、事件、调用效果、日志和 GET。断言取决于场景，改 payload 后应转成 409 的检查，不能沿用成功重放的预期。证据分工回看「四份证据怎样互相补足？」。

### 哪一种检查能回答当前问题，又没经过哪里？

| 当前问题 | 关系或短用法 | 记到什么程度 |
|---|---|---|
| 只想查为什么没发请求，用整套 UAT 吗？ | 纯函数测试固定 `"3"`、`"urgent"`、`"-3"` 的转换与范围，保留被查实现。 | 按当前承诺选小检查，不让最终 201 断言盖住更早原因。 |
| 要查事务有没有一起撤回？ | 在 event INSERT 处受控失败，检查票、事件与计数器；不只断言抛了异常。 | 围绕要保护的状态选择证据。 |
| 要查提交后丢回复是否重复生效？ | partner 测试保留稳定 key 与内容，模拟丢回复，检查 calls=2/effects=1。 | Fake 验证受控边界的本地处理，不证明真实供应商合同。 |
| TestClient 通过，端口就通了吗？ | 它在进程内进入 API；外部 HTTPX 可被 MockTransport 接住，不经过真实 listener。 | **接口行为测试与网络运行证据分开。** |
| 双进程主机检查比它增加什么？ | `host_integration_check.py` 启动 API 与模拟合作方两个进程，经 loopback 真正传 JSON，分别用 tickets.db 与 receipts.db，并查重启持久性。 | 增加 socket、端口、进程证据；仍未经过 Compose DNS、镜像或 named volume。 |
| 受控 AI 测试说明什么？ | 固定坏引用、越权建议，核对拒绝、工具次数与工单不变。 | 证明这套授权和候选检查行为，不证明真实模型的普遍质量。 |

`pytest` 入口与小测试分工回看「为什么还要保留小测试？」；主机检查回看「从进程内协作扩大到两个真实进程」。后者建立并清理自己的临时进程与目录，仍是真实运行动作；只读教材不等于这些检查已执行。

### 一次 UAT 和它的日志，要怎样读才不扩大结论？

| 当前问题 | 关系或短用法 | 记到什么程度 |
|---|---|---|
| X 的一次 UAT 包含哪些交接？ | 创建、同意图重放、GET 读回、政策草稿，四次请求分别取 ID。 | 与 F 的 live/ready/create/read 序列分清；按本例实际入口查。 |
| fresh 与 replay 模式在确认什么？ | `--initial-create-mode fresh` 要求首条新建；replay 要求首条已是旧意图；模式错就失败。 | 模式表达起始事实，不是为了让输出变绿任选。 |
| 切换 AI 场景还要再造工单吗？ | 已完成工单用 replay 起步；close_proposal 应 needs_human、tool_permission_denied、tool_called=false、票仍 open。 | 独立政策请求不改变创建基线；配置恢复也不撤销旧工单。 |
| `uat.py` 知道合作方内部效果有几项吗？ | 它核公开工单、政策状态/原因/来源/工具标记；内部调用效果另由 Fake 记录或专门检查取得。 | **公开 UAT 不能凭空观察远端内部状态。** |
| 正常日志与重放日志为何不同？ | 正常含两次事务与外部尝试；收束后的重放主要记录 intent_replayed；政策有自己的候选检查事件。 | 用阶段链解释当前请求，不要求所有请求走同一链。 |
| 日志说已提交，数据库却没有，信谁？ | 核对日志发生时机与数据库目标；日志文字不能覆盖持久事实。 | 保留不一致并定位，别挑一份绿色证据宣布成功。 |

case_id 是“哪种条件”，request_id 是“哪次 HTTP 处理”，同一用例可发多次请求。普通日志只保留允许的 ID、阶段、结果、版本和计数，不存 subject、prompt、候选正文、token 或原始异常。回看：「一次 UAT 为什么有四个请求编号？」「日志怎样解释一次处理，又怎样保护输入？」。

## X04｜换掉运行实例以后，怎样确认还能服务和恢复？

本章把运行关系接回已经出现的业务事实：**哪份程序 + 哪份配置 + 哪个持久对象 → 当前可观察行为。** 恢复本地数据库还要尊重合作方独立保存的历史。

### 实例换掉以后，究竟接上了哪份数据？

| 当前问题 | 关系或短用法 | 记到什么程度 |
|---|---|---|
| image 相同，就会用同一份数据吗？ | image 由源码、Dockerfile、依赖构建；Compose 另外给环境、端口与挂载，再创建实例。 | 模板不自动包含本次数据与挂载，配置也不把现有数据变成期望内容。 |
| 应用与合作方各写到哪里？ | API：`/data/tickets.db` → ticket-data；模拟合作方：`/partner-data/receipts.db` → partner-data。 | **两个程序、两个持久所有者。** 应用 backup 只处理自己的库。 |
| `/data`、tickets.db 与 named volume 是一个对象吗？ | 分别是容器挂载位置、应用文件、Docker 管理的存储对象。 | 认清文件归属；`/data` 不是固定 Windows 目录。 |
| 从 Windows 与从 API 调合作方，走同一路吗？ | Windows 经主机 18080 转 API 8000；API 经 `fake-partner:9000` 找共同网络的服务。 | 调用位置决定地址；API 的 localhost 只指自己。详细端口关系回 F03。 |
| 重建后怎么证明用了原数据？ | 核对新实例身份与实际 mount，GET 同一工单并检查内容。 | 只看名称或新建成功，不足以证明旧事实保留。 |
| volume 被删除后，再建同名就恢复了吗？ | 同名字符串可以属于新的空对象生命周期；V1/V2/V3 要按实际基线登记。 | **名称相同不等于对象或数据相同。** |

回看：「从源码到文件路径，中间有哪些真实对象？」「普通、降级和版本回归为什么需要不同基线？」。

### 知道版本、ready 与基线以后，可以宣布哪些结果？

| 当前问题 | 关系或短用法 | 记到什么程度 |
|---|---|---|
| D1、D2 只需记录 tag 吗？ | 保存完整 local image ID，再查运行 container 的 `.Image`；真实 registry 分发且确有 RepoDigest 才登记。 | 精确身份与可移动标签分开，base digest 不冒充应用身份。 |
| C1/C2 如何识别运行差别？ | 对按指定顺序合并的 Compose 展开 JSON 文件字节取指纹，同时保留文件与工具来源。 | hash 帮助发现变化，不替代配置文件，也不公开秘密。 |
| X 的 ready 覆盖了 F 的全部检查吗？ | X 查必要数据读取、tickets 可访问和 schema 版本；未逐项核全部列/约束/索引，也未证明所有写能力。 | **不同应用的同名 ready 不可套用范围。** F 的结构与短写探针不自动搬来。 |
| 合作方不可用，为什么 ready 仍可通过？ | X 最低承诺允许本地保存并转人工，合作方是可降级依赖。 | 先依据合同决定能力；实际合同要求确认后才接单时需另设计。 |
| 正常 UAT 的空基线只有应用库吗？ | 应用库与合作方 receipt store 都要符合空基线，才能解释 T-42、PA-1 和一次派单。 | 把两边历史都算进前提，不只重置本地。 |
| 想验降级，用已成功 key 重跑行吗？ | 已收束意图直接读回，不会调用坏合作方；独立降级用另一个 project、端口、两份 volume 与独立 key。 | 选择能真正触发目标分支的基线；改 request ID 不能把旧意图变成新场景。 |

running、live、ready、创建/重放/读回/政策 UAT、备份恢复分别回答不同问题；等待健康也应有明确上限。完整身份、等待与场景配置回看「哪份程序配哪份数据，不能只凭版本名猜」「能响应、准备接单、业务正确是不同的观察」「普通、降级和版本回归为什么需要不同基线？」。

### B1 恢复成可用数据，哪些证据不能合并？

| 当前问题 | 关系或短用法 | 记到什么程度 |
|---|---|---|
| B1 文件存在且 hash 匹配，就证明恢复成功吗？ | 先用 SQLite backup API 取得一致副本，登记来源；再恢复到原本不存在的新目标，核完整性与 schema，最后由隔离 API 读回。 | 副本身份、数据库可用、业务读回是连续但不同的证据。 |
| 恢复文件 hash 必须等于备份文件吗？ | 数据库恢复后物理布局可不同；本例核备份源 hash、恢复 integrity_check 与登记业务字段。 | **数据库恢复不以字节相等为定义。** |
| 默认 restore readback 具体证明什么？ | GET T-42，核设备、主题、priority=3、ticket_status=open；没有新建，也没有重验外部降级或 image 回滚。 | 写明读到的字段，不扩成全部业务规则与完整恢复验收。 |
| 默认隔离脚本会改原数据吗？ | `Invoke-IsolatedRestoreDrill.ps1` 核来源 image/config，建带 label 的新 volume/隔离 API，拒绝覆盖已有目标，默认不联系合作方。 | 明确认读目标与资源副作用；成功只清自己的匹配资源，失败保留现场。 |
| schema=1 与 integrity_check=ok 意味着什么？ | 说明相应版本元数据与数据库完整性检查通过；不表示全部 DDL、约束和业务规则已核对。 | 不把元数据标签或数据库检查扩成业务证明。 |

完整备份与默认隔离读回路线回看「一份 B1，怎样从文件变成可恢复证据？」。命令在明确实验副本中按 RUNBOOK 查用；restore 的目标必须是新对象，不能把旧数据库当练习目的地。

### 应用恢复了，合作方的历史为什么还在？

| 当前问题 | 关系或短用法 | 记到什么程度 |
|---|---|---|
| 从 B1 恢复 tickets.db，会撤销 PA-1 吗？ | PA-1 属于合作方 receipts.db；应用备份没有它，也没有权力让外部世界一起回到备份时点。 | **本地恢复与远端效果直接分开。** |
| 合作方重启后，如何仍认得旧意图？ | 本例把 key、payload 摘要、派单编号与计数持久保存；原 key/内容返回 PA-1，新意图得到下一项。 | 幂等前提是持久 receipt，不只是内存计数或看起来独特的随机编号。 |
| 合作方库丢了，恢复应用 B1 足够吗？ | 已登记恢复路线依赖原 store 继续存在；前提失效需核对外部事实及它的恢复机制。 | 不能宣称本地备份修好了独立所有者。 |
| 恢复后为什么先 replay 旧票再创建新票？ | 旧意图应回 T-42、无新派单；新 key 在恢复库得到 T-43，并由原合作方 store 产生 PA-2。 | 核对两份独立历史继续协调；没有共同事务或共同回滚。 |
| `-RunRestoredUat` 比默认 readback 多做什么？ | 接入已核对的合成合作方网络，先验旧 replay，再验新 T-43 创建/重放/读回/政策。 | **这是新写入，会产生一项远端效果。** 清理隔离 API 不撤销 PA-2。 |
| 恢复后普通 UAT 通过，可覆盖所有失败路线吗？ | 当前子集不含 always_500、close_proposal 权限拒绝或版本回滚；需要时分别给基线与预期再验。 | readback、恢复后指定 UAT、rollback 分别报告。 |

回看：「恢复应用，为什么不能让外部世界一起回到过去？」「恢复后写入，要另做一次什么验证？」。主机双进程验证和容器手册是不同环境的证据，不能互相冒充已运行。

### ready 通过的 D2 为什么仍应退回，交接怎样说清？

| 当前问题 | 关系或短用法 | 记到什么程度 |
|---|---|---|
| X 的受控 D2 哪里坏了？ | uat-regression 仍可读 schema，live/ready 可 200；合法创建在意图事务前返回 503/training_create_regression。 | **健康通过不能代替客户路线。** 与 F 的 D2 schema_mismatch 场景分清。 |
| 只见 503 就能断定这个回归吗？ | 还需具体 detail、无新增票/事件/派单、编号未消耗，才符合本次受控场景。 | 由触发条件与状态证据共同定位。 |
| 退回 D1 为什么不顺手 restore B1？ | 本例 D2 没有破坏性迁移；确认兼容后换回 D1/C1，核实际 Image、ready 与整条新 UAT。 | **程序配置回滚不自动需要数据恢复。** 已迁移数据必须另判兼容与新增事实。 |
| D2/D1 回归的 T-42 是找回旧 V1 吗？ | 本路线在明确的新 V3 基线上进行；沿失败意图原 key/payload 创建 T-42，说明 D2 未消耗编号。 | 不把新基线成功写成已找回被清理的旧数据。 |
| 并发 finalization 后，回复依据谁？ | 以实际已提交状态为准；后完成者记录 assignment_finalize_replayed，不虚构第二次 commit。 | 恢复或回滚不跳过原有状态保护。 |
| runbook 要交出哪些判断？ | 实验目录、project/端口、image/config/data 身份、输入与期望、失败停止处、保留及清理精确对象的方式。 | 让下一操作者无需猜前提；完整命令按阶段查，不机械串接。 |
| `down --volumes` 会影响谁？ | 本 project 相关 volume，包括应用库和模拟合作方库；普通 down 默认保留 named volume。 | 数据丢弃是单独决定，需精确 label、内容与恢复安排；不能用 prune 处理其他项目。 |

回看：「D2 可以 ready，为什么仍然不能采用？」「让另一位操作者可以按说明做完」。最终记录注明目标环境、对象身份、实际输出和结论范围；未运行仍是未验证，失败仍按失败登记。静态声明检查、Fake 计数、主机进程测试均不能写成真实容器网络与挂载已通过。

跨册查找时，先说清现在不确定的交接：文字变值回 A；HTTP 消息与回应检查回 B；行/事件/计数共同提交回 C；未知外部效果与稳定意图回 D；资料、候选和动作授权回 E；image/config/volume 与恢复回 F。它们在同一应用的多个位置起作用，不是一条 A→B→C→D→E→F 的请求流水线。整体关系见原教材「关系收束｜从一个现象找到下一项有用证据」。
