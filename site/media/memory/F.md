# F 册｜章节记忆与查用

这份表帮助找回交付时容易混在一起的对象：交出的程序、正在运行的实例、本次配置、持续保存的数据，以及证明结果的记录。按当前问题查，不要求背完命令再继续。

**关系要能解释，常用操作逐渐用熟，长配方带着目的查。** 查用时仍要认清执行位置、目标对象、会改变什么和成功证据；备份、恢复、替换与清理尤其需要这些信息。

**表里的 Docker 指令和对象名先按“模板、实例、进程、数据、证据”的角色理解。** 英文名用来回到命令或运行手册定位，不要求把整套参数背下来；实际操作前先核对目标和可观察结果。

F01–F02 连接源码、镜像和实例；F03 连接请求入口与持久存储；F04 判断当前能力；F05–F06 连接恢复、验收和交接。它们共同描述一套运行组合，不是六个依次处理请求的服务。

本册小应用只查询模拟容量，不创建外部预约，也没有工单创建幂等接口。它使用自己的数据库：`capacity_confirmed` 不等于 X 册的 `partner_confirmed`；同名 T-42 也不表示两册共用记录。

下文“回看”指 F 册原教材的同名小节。完整操作在独立实验副本 `support-stack` 的 `RUNBOOK.md` 查用；从可见入口 `02_配套代码_F与综合应用/examples/f_delivery_observability/support-stack` 复制完整项目。它与底层 `02_配套练习_FX新版` 指向同一份配套，不用再找另一套“新版”。这里的路径、编号、D1/C1/B1 和输出都是教材示例或代号，不是当前电脑的实测状态，也不是立即执行的指令。

## F01｜一份程序怎样成为一次运行

先抓住对象关系：**构建输入形成 image；image 加上本次配置建立 container；container 中的主进程执行指定工作。** 若入口是服务，它会持续处理请求；若入口只是打印版本，完成后就结束。一份模板可以产生多次运行，每次都有自己的身份和状态。

### 模板、实例与进程，哪一个正在工作？

| 当前问题 | 关系或短用法 | 记到什么程度 |
|---|---|---|
| image 中已经有程序，为什么还不能接请求？ | image 保存文件、运行时、库和默认命令；它本身没有正在等待请求的进程。container 创建后还需启动，才能运行指定主进程；主进程还须实际提供服务。 | **模板、实例存在和服务可用直接分清。** 镜像存在不等于服务已启动。 |
| 同一 image 启动两次，会共享同一个进程吗？ | 两个 container 有不同 ID、主进程、日志与可写层；`.Image` 可以相同。 | 能解释“同一模板、不同实例”；名字和 ID 用实际值。 |
| 容器是复制了一整台 Windows 吗？ | 本例是 Linux 容器；Windows 提供终端，Docker Desktop 提供相关后台环境，容器内使用 Linux 路径与运行约定。 | 分清命令发起处和程序运行处；隔离实例仍使用主机资源，也可能因配置错误失败。 |
| `docker run` 做了什么？ | 建立并启动新实例；`-d` 让它后台运行，`--name` 给实例名称。 | 逐渐认熟动作；完整命令查原章。新实例名称已存在时先核对对象，不覆盖旧实验。 |

回看：「image 提供模板，container 保存这一次实例」。

### 命令报错或服务停了，先看哪个入口？

| 当前问题 | 关系或短用法 | 记到什么程度 |
|---|---|---|
| PowerShell 找到了 `docker`，就能管理容器吗？ | PowerShell 启动 Docker CLI；CLI 向当前连接的 daemon 发请求，由后台服务管理对象。 | **命令行入口存在，不等于后台可达。** Docker Desktop 界面也不替代业务证据。 |
| `docker version` 的 Client 和 Server 分别说明什么？ | Client 对应终端调用到的 CLI；Server 对应已联系的 daemon。只有 Client 后接连接错误，尚未走到应用。 | 认熟两部分；不要由连接失败推断镜像坏了。找不到 `docker` 则停得更早。 |
| 哪些实例在运行，停下来的还在吗？ | `docker ps` 看运行中的容器；`docker ps -a` 也看已停止实例。 | 逐渐用熟两种范围；列表为空不一定表示对象从未存在。 |
| 要看实际镜像、命令和退出码，用什么？ | `docker inspect 名称` 读结构化对象信息；按问题选 `.Id`、`.Image`、状态、入口与退出码等字段。 | 知道去哪里取证，不背全部输出或完整格式模板。 |
| 程序打印了什么，用什么查？ | `docker logs 名称` 查看程序写到 stdout/stderr 的内容，受实际日志配置影响。 | 能用日志解释过程；日志不是数据库，也不保证包含所有内部行为。 |
| Exited (0) 为什么仍不能提供 API？ | 主进程若只是 `python --version`，打印版本后正常结束，容器随之停止。0 表示这条命令正常结束。 | **正常退出与持续服务不同。** 结合入口、状态和日志判断，重启同一入口只会再次结束。 |

回看：「终端里的命令由谁执行」「主进程退出时，容器为什么停了」。

### 停止、删除和重新创建，各留下什么？

| 当前问题 | 关系或短用法 | 记到什么程度 |
|---|---|---|
| `stop` 会删除程序吗？ | 停止目标实例的主进程；实例信息仍在，不删除主机源码或 image。 | 认熟停止的对象范围。 |
| `rm` 后为什么临时文件不见了？ | 删除目标 container 及其可写层；后来写在这一层的文件随实例消失。 | **删除实例与停止实例直接分清。** 先核对精确名称及归属。 |
| 用同一 image 新建实例，能找回上次工单吗？ | image 不自动收集旧实例运行后的业务数据；需要新实例重新接上独立持久存储。 | 能把数据保留问题交到 F03，而不是认为“镜像相同就什么都相同”。 |

只删除 C1 不会顺带删除未被指向的 C2、image 或主机源码；挂载存储又有自己的生命周期。完整停止、删除示例回看「停止与删除分别留下什么」，运行前按自己的对象核对。

## F02｜Dockerfile 怎样把文件变成运行模板

本章追的是：**明确构建输入 → 在镜像环境执行构建步骤 → 得到可识别的 image → 启动时采用默认命令。** 构建发生在哪里、启动发生在哪里，会决定下一步选什么操作。

### builder 从哪取文件，怎样限制输入？

| 当前问题 | 关系或短用法 | 记到什么程度 |
|---|---|---|
| `docker build ... .` 最后的点是什么？ | `.` 选择当前目录为 build context，即本次本地构建输入范围；`-t` 为产物指定 tag。 | 认熟“构建说明”和“可见输入范围”两件事；换 Dockerfile 不会自动改 context。 |
| `COPY` 能随意取电脑上任何文件吗？ | 普通本地 COPY 的来源受 context 与排除规则限制；目标是镜像中的路径。 | 沿“主机输入 → image 目标”找文件，不把两端路径混成同一位置。 |
| 为什么排除虚拟环境、数据库和备份？ | `.dockerignore` 在构建输入阶段排除匹配内容；配套还排除 `.env`、缓存和 tests。 | 理解排除能减少无关输入与误带数据；具体规则查文件。 |
| 秘密先 COPY，再删除，就安全了吗？ | 早期层仍可能保存它。真正的 build secret 要用专门的 secret mount，不能以普通 ARG/ENV 或后续删除替代。 | **进入过构建层的内容，不因后面删掉就从历史消失。** 本例无需真实凭据。 |

构建会产生或复用镜像与缓存，可能需要取得基础镜像；它不会自动替换正在运行的所有容器。完整 build 参数、目录材料和 `.dockerignore` 回看「builder 能看见哪些文件」。

### Dockerfile 中哪些在构建，哪些等启动？

| 当前问题 | 关系或短用法 | 记到什么程度 |
|---|---|---|
| `FROM`、`COPY` 分别接上什么？ | FROM 选择已有基础镜像；COPY 再加入本项目文件。Python 基础镜像不自动含本项目源码。 | 认熟来源方向，不把 base 当最终应用。 |
| `RUN` 和 `CMD` 是同一时机吗？ | RUN 在 build 环境中执行；CMD 给容器启动提供默认命令。把长期服务写入 RUN 会让构建等待它结束。 | **构建动作与运行入口直接分清。** 只把安装写成 CMD，安装结束后实例也可能结束。 |
| `WORKDIR /app` 改了谁的目录？ | 设置镜像中后续相对目标与默认进程工作目录；没有把 Windows PowerShell 切到 `/app`。 | 认熟作用位置；不是主机的 `Set-Location`。 |
| `ARG`、`ENV` 怎样连接默认值？ | ARG 提供构建参数；本例再用 ENV 把版本等默认设置保留到 image 配置，运行时可覆盖适合变化的值。 | 分清构建输入与运行环境；完整覆盖规则按需查。 |
| `USER` 后非 root，为什么仍可能写不了数据？ | 本例先建用户、目录并设置权限，再以 `10001:10001` 运行；实际挂入的存储也必须可访问。 | 用户与路径权限一起看；不能只复制 USER 而省略条件，也不能由非 root 推断全面安全。 |
| `CMD ["python", "app.py"]` 的方括号怎样读？ | exec form 把可执行程序与参数分成数组元素，不要求 shell 解释整段文字。 | 能看出实际入口；完整 Dockerfile 查用，不要求默写。 |
| `EXPOSE 8000` 已经开好主机端口了吗？ | 只记录预计端口元数据；应用要实际监听，运行配置要实际发布主机入口。 | **声明端口、监听端口、发布端口分开。** F03 再追请求。 |

回看：「一份实际 Dockerfile 怎样读」。

### 改了文件或版本，选 rebuild、recreate 还是 restart？

| 当前问题 | 关系或短用法 | 记到什么程度 |
|---|---|---|
| 只改源码，为什么先复制依赖有用？ | 依赖清单未变时可复用安装步骤；清单变了，后续相关结果需要重新计算。 | 理解 build cache 复用输入对应结果；`CACHED` 不证明业务正确。 |
| `--no-cache` 与 `--pull` 能互换吗？ | 前者要求不复用构建缓存；后者尝试取得指定 base 引用。base 固定 digest 时，pull 不会替你挑选新版本。 | 认得不同目的，其余参数查用；安全更新仍需明确变更和验证。 |
| tag、base digest、最终 image ID 分别标识谁？ | tag 是可移动的可读名字；base digest 固定基础内容；最终 image ID 还对应加入源码和配置后的应用产物。 | **基础身份不能冒充最终应用身份。** D1 是记录实际 ID 后的讨论代号。 |
| source、依赖或 Dockerfile 改了？ | rebuild 产生新 image，再用它建立新 container。 | 能按变化对象选动作；build 成功不会自动更新已有实例。 |
| 只改本次端口或环境变量？ | recreate 用新运行声明建立实例；源码不变时无需只为此重建 image。 | 分清模板变化和实例配置变化。 |
| 只是让同一实例的进程重新开始？ | restart 保留原镜像与原运行配置。 | 认熟重启的边界；它不会重新注入刚修改的 Compose 配置。 |

需要确认最终产物时，用 `docker image inspect` 查实际 ID、Cmd、User；这是身份与默认入口证据，不替代 API 验收。完整命令回看「固定身份与更新并不冲突」；缓存见「为什么先复制依赖，后复制源码」，动作选择见「改了文件以后应该做什么」。

## F03｜请求怎样进入，数据怎样留下

一次运行需要接通三条关系：**Windows 请求 → API listener；API → 容量服务；SQLite 文件 → 挂载存储。** 其中一条成功不替另外两条作保证。

### 配置写在哪，程序何时取得？

| 当前问题 | 关系或短用法 | 记到什么程度 |
|---|---|---|
| 同一 image 为什么能当 API，也能当容量服务？ | 启动入口读取 `SERVICE_ROLE`、监听地址和端口；不同实例通过环境得到不同角色。 | 认清 image 相同与运行配置不同可以同时成立。 |
| `os.getenv("SERVICE_ROLE", "api")` 读到什么？ | 从当前进程环境取文字；缺失时用默认值。端口文字还要转换成整数，转换失败就停止启动。 | 逐渐认熟“读取 → 转换 → 影响行为”；环境变量不会自己执行代码。 |
| 修改 Compose 后，旧进程为什么还用旧值？ | 进程已经读取启动环境；需要用新声明建立实例，restart 仍用原注入值。 | **配置文件变化与进程实际配置分开。** |
| Compose YAML 是逐行执行的脚本吗？ | 它描述 services、image、environment、ports 和 volumes；缩进表达从属，`-` 表示列表项。 | 能看出字段属于谁；service 名称不是源码文件名。 |
| 目录里有 `.env`，程序就会拿到全部变量吗？ | 主机 `.env` 可供 Compose 替换 `${变量}`；进程环境还要经过镜像默认值、本次注入与覆盖规则。 | 分清“展开声明”和“注入进程”；不靠文件存在推断实际值。 |

完整声明使用配套 `compose.yaml`，不把原章的关系切片当完整运行文件。回看：「环境变量怎样变成进程行为」「Compose 把相关实例放进一份声明」。

### 同一个 localhost，站在哪一边看？

| 当前问题 | 关系或短用法 | 记到什么程度 |
|---|---|---|
| `127.0.0.1:18080:8000` 怎样读？ | 主机只在 loopback 发布 18080，转到容器 8000；Windows 客户端访问前者。 | 逐渐认熟“主机地址 : 主机端口 : 容器端口”；两边数字不必相同。 |
| 应用监听 `0.0.0.0:8000`，客户也访问这个地址吗？ | 它表示在容器网络空间的各接口监听；客户使用实际可达的主机地址。 | **监听范围不是客户目标地址。** 容器内仅监听 127.0.0.1 时，发布请求可能到不了该 listener。 |
| API 为什么访问 `fake-dependency:9000`？ | 同一 Compose 网络按 service 名称解析当前容量实例，使用内部端口；不必把容量端口发布到 Windows。 | 认清内部服务交接；主机 18080 不参与这一次调用。 |
| API 的 `localhost:9000` 指容量服务吗？ | 它指 API 容器自身；容量容器与 Windows 也各有自己的 localhost。 | **同一写法取决于所在网络空间。** |
| inspect 查到 IP 后，可以写死到源码吗？ | 重建后 IP 可能变化，服务名可重新解析当前实例；旧连接失败仍需处理与重新连接。 | 知道名称稳定不等于连接永远有效。 |
| `depends_on: service_healthy` 能保证依赖一直好吗？ | 配套用它等待初始健康条件；容量探针测 `/live`，以后 `/capacity` 仍可能 503。 | 分清启动顺序与持续业务能力，不把依赖图当永久保证。 |

容量调用在 `/capacity` 上做有界 GET。本例只核对 JSON 对象和 `status == "available"`，`slots` 不参与决策，因此不能说已验证全部容量字段合同。回看：「18080 与 8000 分别属于谁」「API 为什么用服务名称，而不用 localhost」。

### 文件名、挂载点和 volume，哪一个保存工单？

| 当前问题 | 关系或短用法 | 记到什么程度 |
|---|---|---|
| `/data/tickets.db` 与 `ticket-data:/data` 怎样连起来？ | 应用打开前一个文件；后一个把 named volume 挂到 `/data`，该目录中的写入进入挂载存储。 | 沿“文件 → 挂载点 → 存储对象”追踪；三者不是同一名称。 |
| 数据写在 `/app/tickets.db`，为什么换实例后没了？ | 未挂载该位置时，运行中新增文件属于实例可写层；停止再启动同一实例通常保留，删除后重建不会带回。 | **同实例重启和替换实例不同。** |
| named volume 与 bind mount 何时选？ | 本例数据库用 Docker 管理的 named volume；操作者要取得备份，用明确主机目录挂到 `/backups`。 | 按数据用途选择；Windows 路径与容器路径分别核对。 |
| Compose 里写 `ticket-data`，实际对象就叫这个吗？ | 它是逻辑名，实际名称通常带 project 前缀；按 inspect 和项目 label 辨认。 | 不猜 Docker Desktop 的内部磁盘目录，不靠相似名称认对象。 |
| 有 volume，误删数据也能恢复吗？ | 它解决跨实例保留；应用误删、删除 volume 或底层损坏仍可能丢数据。 | **持久存储不等于独立备份。** F05 处理恢复。 |

回看：「SQLite 写入的文件实际属于谁」。

### 声明可解析以后，还缺哪一段证据？

| 当前问题 | 关系或短用法 | 记到什么程度 |
|---|---|---|
| `docker compose config --quiet` 成功，能直接说启动成功吗？ | 它只检查声明能解析；不证明端口空闲、进程可启动或数据库可写。 | 认熟静态检查的结论范围。 |
| Compose 等健康与主机 HTTP 检查重复吗？ | 前者等待所配置的运行/健康条件；后者经过 Windows 发布端口再访问 `/ready`。 | 根据观察位置选检查；内部成功尚未覆盖主机入口。 |
| 怎样证明替换实例后保留了原数据？ | 对比旧/新容器 ID、实际 mount，再 GET 原 T-42 并核对字段。 | **新建成功不能代替旧数据读回。** 新工单会掩盖原数据是否仍在。 |

启动会创建运行对象；首次 UAT 会写入，必须接上已确认的空基线；force-recreate 会替换实例。完整顺序、等待参数和失败处理回看「怎样用一次运行把声明与结果接起来」及 F06，不从表中拼一套立即执行的命令。

## F04｜进程活着，为什么还不能接单

健康判断要接回承诺：**进程能响应什么探针，核心数据满足什么条件，客户路线实际完成了什么。** 这些是不同层次的观察。

### running、live、ready 与 healthy，各自说明什么？

| 当前问题 | 关系或短用法 | 记到什么程度 |
|---|---|---|
| container running 说明能接单吗？ | 只说明主进程仍存在；还要看请求入口与应用处理。 | 分清进程状态和业务能力。 |
| `/live=200` 为什么可能同时 `/ready=503`？ | live 检查进程能响应最小探针；ready 检查当前核心数据条件。 | **liveness 与 readiness 直接分清。** 其语义由应用设计，不由端点名字自动保证。 |
| 本例 `/ready=200` 具体覆盖什么？ | schema 版本、约定核心表结构与短写入探针通过；不是所有未来请求的保证。 | 能说出实际检查范围，不只记“服务准备好了”。 |
| Docker healthy 从哪里来？ | Docker 执行指定 healthcheck，按退出码和配置维护 health 状态；本例 API 探针测容器内 `/ready`。 | 先查探针测什么；换成 `/live` 后，同一 healthy 文字的含义会变。 |
| 健康通过还要 UAT 吗？ | 创建后读回关键字段一致，才覆盖这一条业务保存与读取；容器内探针还未经过主机端口。 | **健康检查与业务验收不能互相代替。** |

探针成功退出 0，失败非 0；状态从 starting 开始，一次成功可到 healthy，连续失败按 retries 进入 unhealthy。`start_period`、`interval`、`timeout` 的完整配置按需查，状态也有更新时差。本例未设置健康失败自动重启；unhealthy 不自动回滚工单。

回看：「Docker health 是怎样得到的」。

### 什么条件必须阻止写入，什么失败可以转人工？

| 当前问题 | 关系或短用法 | 记到什么程度 |
|---|---|---|
| 实际 schema 1，D2 期望 2，会发生什么？ | 创建路由先做 core_readiness，返回 `schema_mismatch` 与 503；本例尚未读请求正文、查容量或 INSERT。 | 先定位拒绝时点，再判断已发生的效果；不是进程已死。 |
| metadata 写着 1，表结构就一定正确吗？ | 配套还用 `PRAGMA table_info` 核对列名、类型、NOT NULL、默认值、主键，并检查工单自增约定。 | 版本标签和实际结构分开；不符为 `schema_structure_mismatch`。 |
| 怎样检查现在可写，又不制造工单？ | 短事务写 readiness_probe 后 rollback；不留下业务记录，也不消耗工单编号。 | 认清探针写入目标和撤回范围；当前通过不保证下一时刻无锁或故障。 |
| 容量失败，API 为什么仍 ready？ | 本例最低承诺是持久保存并可转人工；容量属于可降级能力，不决定核心 ready。 | 从服务承诺决定依赖重要性，不能套用“所有依赖都必须进 readiness”。 |
| `manual_review` 与 `capacity_confirmed` 都返回 201，含义一样吗？ | 前者表示容量路线未完成、工单已保存需人工；后者表示本例容量约定已确认。 | **请求创建成功与自动处理完成分开。** 本例只存状态，真实人工队列和响应时限尚未实现。 |

配套临时 SQLite 小例可以观察“同一份数据、不同版本期望”的结果，但它不启动容器。回看：「就绪检查怎样阻止不兼容的写入」「可选容量失败为什么得到不同结果」。

### 看到失败原因，怎样找到下一份证据？

| 当前问题 | 关系或短用法 | 记到什么程度 |
|---|---|---|
| 日志里有 T-42 相关请求前缀，就表示创建过吗？ | 关联前缀帮助归组；`R-F-42-CREATE` 与 `R-F-42-READ` 是不同请求。503/schema_mismatch 日志恰好可能表示写入前拒绝。 | request ID 连接处理，不替代工单事实。 |
| 应按什么找日志？ | `docker compose ... logs api` 取得服务输出，再按本次 request ID 筛选，核对 method、规范路径、status 和 reason。 | 逐渐用熟按请求查，而不是只搜索“error”；完整项目参数查原章。 |
| 缺日志能证明操作没发生吗？ | 收集、驱动或查询条件都可能造成缺失；保留响应、时间与请求 ID，再找数据证据。 | **缺一份过程记录不等于没有效果。** |
| 排障可以把整个环境与请求都打印吗？ | 本例只记允许字段；工单路径规范成 `/tickets/{ticket_id}`，未知路由用占位名，避免正文或 URL 私密文字入日志。 | 认清记录用途与内容范围；不打印 body 也不等于所有日志都安全。 |

已有 `schema_mismatch` 时，下一步核对镜像期望和数据版本；主机失败但容器探针成功时，回 F03 看发布路线。按最早偏离选证据，不必每次按同一清单全部检查。回看：「日志怎样帮助找到最早偏离」。

## F05｜怎样证明备份能恢复，并回到已知版本

备份与恢复连接的是：**明确来源与时点 → 一致副本和清单 → 新目标恢复 → 数据核对 → 应用读回与新写入。** 回滚再决定要换程序、配置还是数据。

### 有备份文件以后，怎样知道里面是需要的事实？

| 当前问题 | 关系或短用法 | 记到什么程度 |
|---|---|---|
| volume 为何不能给自己兜底？ | 误删与错误迁移仍作用于其中的数据。B1 放在独立的主机备份目录，与运行 volume 分开。 | 理解独立备份用途；同一机器上的副本不代表异地容灾。 |
| 为什么不用随手复制正在写的 `tickets.db`？ | SQLite 的已提交状态可能还涉及 WAL；`source.backup(destination)` 由引擎取得一致视图。 | **文件复制与数据库一致备份分开。** 其他数据库查自己的机制。 |
| `integrity_check`、hash、行数、关键字段可以只留一个吗？ | 分别检查数据库完整性、文件变化、数量和业务内容；各自排除不同问题。 | 能解释证据用途；文件非空、hash 匹配都不证明选对业务时点。 |
| 两张工单，下一编号一定 T-44 吗？ | 删除过记录后，数量与已用编号不同；配套从 SQLite 序列与当前最大 ID 得出 next_ticket_id。 | **下一编号从实际序列取得，不用数量推算。** |
| SHA-256 匹配就证明来源可信？ | 它不是签名；备份与清单若同时被替换仍可能匹配。还需受控来源、登记身份与时点。 | 不把完整性比对扩成来源认证。 |

B1 清单同时保存实际 schema、工单数、下一编号、T-42 的设备/症状/处理状态/创建时间，以及 image/config 身份。占位文字不能充当实际值。回看：「一个 volume 为什么不能给自己兜底」「B1 清单里的每个值都要从数据取得」。

### 说“回到旧版本”，究竟要保存哪种身份？

| 当前问题 | 关系或短用法 | 记到什么程度 |
|---|---|---|
| `1.1.0` 与 D1 足够吗？ | 版本是沟通标签，D1 是本文代号；应登记容器 `.Image` 对应的实际完整 image ID。 | **名字正确不等于运行内容正确。** |
| local image ID、base digest、RepoDigest 能混用吗？ | 分别对应本 Docker host 的精确应用镜像、构建基础内容、真实 registry 分发内容。纯本地构建可能无 RepoDigest。 | 按对象登记；没有就写没有，不用 base digest 冒充应用分发身份。 |
| C1 配置 hash 能恢复配置吗？ | 指纹帮助发现已展开声明的变化；仍需原 Compose 文件、project、覆盖来源和工具版本。 | hash 不是文件备份；跨机器路径或工具输出也可能改变 hash。 |
| 新终端怎样取得“旧 D1/C1”？ | 从升级前保存的清单读取，再与现场核对；现场重新计算的是当前值。 | **当前值不能事后改名成旧基线。** |

`Get-ComposeConfigFingerprint.ps1` 用来为当前展开配置取指纹；取身份前要确认 api 容器唯一且属于目标 project。完整命令与字段用途回看「先取得正在运行的精确身份」。

### backup、verify、restore 与 rollback，各改变哪里？

| 当前问题 | 关系或短用法 | 记到什么程度 |
|---|---|---|
| backup 和 verify 为何分开？ | backup 新建一致备份及清单；verify 重新核 hash、完整性、结构、版本、数量、下一编号和关键字段。 | 知道创建产物后还需重新核对；同名 B1 已存在时拒绝覆盖。 |
| 管理命令为什么也有一个 container？ | admin service 用同一 image，通过 entrypoint 运行 `data_admin.py`；`run --rm` 的临时实例完成管理动作后清理。 | 临时实例不是临时数据；volume 与主机 backups 仍有各自生命周期。 |
| 什么地方才可用 immutable 读取？ | 配套只对已关闭、固定不变的备份使用此约定；运行中的源库可能变化。 | 不把特定读取前提当活跃数据库提速技巧。 |
| 隔离恢复往哪里写？ | 新 volume、新容器和备用端口；先验证备份，再写新目标的 `.partial`，验证后建立最终数据库。 | **恢复不覆盖仍正确的原数据。** 目标或临时文件已存在就停止，异常不退成无条件覆盖。 |
| 恢复后为什么既读 T-42 又创建新工单？ | 读回原关键字段证明旧事实可用；按清单 next 创建并读回新记录，证明恢复应用可继续写。 | 读回与新写入分别有用途，不以“库能打开”代替业务恢复。 |
| 隔离 UAT 为什么得到 manual_review？ | 本例故意让容量不可达，验证隔离数据的读取、写入与人工路线；原环境另验正常容量。 | 结论写明隔离配置，不能说它逐项复原了原 Compose 网络。 |
| 回滚 D2 一定要把 B1 覆盖回来吗？ | 本例 D2 仅改 schema 期望，没迁移数据；核对 D1/C1 后用原 volume 重建，再验 ready、旧记录与新 UAT。 | **rollback 是回到兼容组合；restore 是从备份建立数据目标。** 两者不是同义词。 |
| 真正迁移过 schema，还能只换旧 image 吗？ | 先判断旧程序是否兼容；可能要恢复到另一个目标并明确切换，处理备份以后新增的事实。 | 已提交迁移不能用旧事务 rollback 撤销；换程序不保证数据兼容或不丢新事实。 |

完整 backup/verify 命令回看「创建备份与验证是两个动作」。隔离演练脚本 `Invoke-IsolatedRestoreDrill.ps1` 会新建资源并做新写入；成功时按精确标签清理自己的资源，失败时保留，`-KeepEvidenceResources` 可保留成功现场。备用端口被占时停止，不结束未知进程。执行位置、参数与原环境不变的核对见「隔离恢复如何走到业务结果」。

回滚长配方见「回滚程序什么时候不需要恢复数据」及 RUNBOOK：先核对旧身份与配置，再按已登记镜像替换，防止恢复过程中重建或拉取另一内容；最后再看运行中 `.Image`。结论依据数据结构、关键业务字段和后续行为，不能把“恢复文件字节完全相等”当恢复成功的通用定义。

## F06｜怎样让另一位操作者完成验收与交接

交接要让下一位操作者取得同样明确的输入与判断依据：**在哪运行、操作谁、预期留下什么、失败停在哪里、之后怎样恢复或暂停。** runbook 是这条操作接口，UAT 是其中对客户路线的验证。

### 验收要观察什么，为什么重跑可能改变现场？

| 当前问题 | 关系或短用法 | 记到什么程度 |
|---|---|---|
| UAT 只看首页或内部函数吗？ | 本例依次请求 live、ready、创建与读回；核对工单编号、状态、设备、症状、创建时间及请求关联。 | 按客户可见任务选证据，不用端口可达代替保存正确。 |
| 一次 UAT 为什么有四个 request ID？ | 四次 HTTP 请求分别取 LIVE、READY、CREATE、READ 后缀；前缀归组，不把它们合成一次请求。 | 认熟“验收场景”与“本次请求”的不同粒度。 |
| `data_classification=synthetic` 能证明没用真数据吗？ | 它是显式输入合同，不会自动识别任意文字的真实来源。 | 本例仍只使用自己的合成输入，也未实现登录系统。 |
| 创建返回 T-42，就可以跳过读回吗？ | 后续 GET 还要与创建返回的全部关键字段一致；相同编号可能对应已变化内容。 | **结果编号与内容一致性分别看。** |
| UAT 失败了，直接再跑一遍可以吗？ | 可能已经创建后才在字段或读回处失败；本例无创建幂等，重跑 POST 会新增工单。 | 先看失败 step、实际返回编号和现存记录，再确定下一步。不能把重跑当继续上次。 |

完整输入和四次交换回看「先写客户要看到的结果」；入口 `uat.py` 的完整参数和副作用回看「从全新环境完成一次连续验收」。

### 一条操作说明，怎样使失败停在正确位置？

| 当前问题 | 关系或短用法 | 记到什么程度 |
|---|---|---|
| “运行 Compose，确认成功”缺了什么？ | 缺实验目录、project、端口、等待条件/上限、成功输出与失败处理。 | 能把动作写到实际对象和可观察结果上。 |
| 原生命令失败，为什么后面仍可能继续？ | PowerShell 需按相应流程判断 `$LASTEXITCODE`；本例非 0 就抛错停在该步骤。 | 逐渐认熟退出码用途；不要只看终端最后一行。 |
| 等几秒够不够？ | 等待应围绕 ready 等可观察条件，设预算；到期不发后续轮询，晚返回的成功也不计预算内通过。 | 分清有界等待与固定睡眠；单次底层 I/O 仍有自己的 timeout 语义。 |
| 数据库 count=0 就是首次基线吗？ | 还需下一编号 T-42；曾创建后删除可能留下不同序列。baseline 只读核对。 | **干净基线由实际数据与序列共同确定。** 不为变绿清空未知 volume。 |

回看：「一条操作说明怎样做到可执行」。

### 多条验收路线怎样共享数据，又怎样保持独立？

| 当前问题 | 关系或短用法 | 记到什么程度 |
|---|---|---|
| 首次正常路线留下什么？ | 已核对空基线，创建/读回 T-42，状态 capacity_confirmed；D1/C1 与请求记录可追踪。 | 样例编号来自这份基线，不能套到任意现存数据库。 |
| 替换 API 后验什么？ | 新实例 ID、同一 volume、原 T-42 全部关键字段仍在。 | 验实例替换与旧数据关系，不重新造一张代替。 |
| 原环境容量降级后有什么变化？ | 新建 T-43/manual_review，API 仍 ready；恢复容量后原库有两张票，B1 下一编号 T-44。 | 用独立请求前缀并保留实际状态变化。 |
| 隔离恢复创建 T-44，会消耗原环境编号吗？ | 新 volume 有自己的序列；隔离创建 T-44/manual_review，原库仍两张，下一编号仍 T-44。 | **编号相同不代表同一数据库或同一事实。** |
| D2 回滚后怎样接着验证？ | 本例数据没迁移；回到精确 D1/C1 后，原环境再建 T-44 并验证正常路线。 | 根据已发生的步骤取下一编号；完整实验有依赖顺序，不能随意重复。 |

前置检查、构建、正常、替换、降级、备份、隔离恢复、D2/回滚与交接的完整顺序，回看「从全新环境完成一次连续验收」。长命令按 RUNBOOK 所在阶段查用；不要从不同阶段各取一条拼接。

### 最终交给别人什么，暂停时又会留下什么？

| 当前问题 | 关系或短用法 | 记到什么程度 |
|---|---|---|
| 只有源码版本为什么不够？ | 还需实际 image ID、构建来源、Compose/project/配置指纹、端口与挂载、schema/volume 身份、B1 和恢复结果。 | **交接的是可识别的程序、配置、数据组合。** 指纹不能替代原文件。 |
| 所有验证都写“通过”行不行？ | 分别写单元/主机双进程/容器/客户路线/恢复/另一操作者完成到哪里。 | 进程内测试与静态 Compose 检查不证明真实容器、网络、挂载或文档可操作。 |
| ready 通过但读回错，怎样交接？ | 保留目标身份、请求 ID 与字段差异；客户路线仍失败。备份 hash 不符则停止升级并保留原正确数据。 | 失败出口接回具体证据，不以局部绿色状态盖过业务失败。 |
| `stop`、普通 `down`、`down --volumes` 差在哪？ | stop 保留实例；普通 down 删除本 project 的容器和网络，保留本例 named volume；带 volumes 会扩大到数据卷。 | **数据删除范围必须单独认清。** 先看精确对象及 label，再作已决定的暂停或结束操作。 |
| 一个项目出错，可以用 prune 清一遍吗？ | prune 面向更广的未使用资源，范围超出当前一次故障；F01 独立容器也不属于此 Compose project。 | 按明确对象处理，不靠全局清理代替定位。 |
| 共享清单要贴全部环境和日志吗？ | 只保留核对所需字段，另记操作者、时间、失败联系人与证据位置。 | 日志和 inspect 输出可能含敏感内容；信息够判断即可。 |

回看：「交接清单为什么同时保存程序、配置和数据」「失败出口与日常停止同样属于交付」。另一位满足前置的操作者实际完成路线，才增加“文档足以交接”的证据；阅读或维护这份辅助表不构成运行成功或学习掌握的记录。

跨章查找：构建输入不清回 F02；请求到不了回 F03 的端口；替换后数据不见回 F03 的挂载；live/ready 不同回 F04；旧程序配哪份数据回 F05；步骤仍需猜测回 F06。multi-stage、registry 等扩展只在项目需要时进入，见原教材「什么时候再进入构建与分发扩展」。版本敏感选项在实际操作时从「官方查用入口与版本边界」核对。
